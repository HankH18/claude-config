# Swarm Loop

This skill turns a project description — ideally a build-docs doc set — into working software in **two acts**, both metric-driven against goals **defined and frozen at the very start**:

1. **The build** — every ticket runs through a readiness scheduler: a ticket dispatches the moment its dependencies are closed, its blast radius overlaps no in-flight writer, and merge-review bandwidth allows. Waves are *emergent batches*, not planned rounds, and the swarm stays as wide as non-interference permits. Each integrated batch passes the verification ladder; a "cycle" survives as the measurement epoch — the heartbeat at which the frozen metrics are measured, the regression re-fit, and priorities re-steered — not as a planning unit. "Measurement epoch", "merge-review bandwidth" and the autonomy modes each gate real behaviour and each has a mechanical definition below; read those three before running anything.
2. **The audit-fix loops** — once every ticket (including every minted bug ticket) is closed, a user-set number of loops each audit the **entire codebase in parallel**, convert findings into tickets, and resolve them through the same scheduler before the next loop re-audits everything fresh. A loop that finds nothing worth fixing ends the run early, through the prune gate.

Two feedback loops run at once, and both matter:

1. **The product loop** — the codebase converges on the frozen goals. Each cycle's regression analysis (error slope, projection to the final cycle, per-metric verdict) decides what the next cycle works on and how hard.
2. **The process loop** — the orchestration itself improves, starting inside the very first cycle. At every **wave boundary** and every **cycle boundary**, record what went wrong with *how you ran the swarm* (task sizing, prompt gaps, merge collisions, wave ordering) in a learnings file, and apply those corrections to the very next wave's packets and the next cycle's decomposition. At the end of the run, distill durable lessons into this skill's own `LEARNED.md` so future runs start ahead.

The design borrows deliberately: from the Ralph-loop school, that **progress lives in files and git history, not in the context window**, and that success criteria are defined up front so iteration has something to converge on; from Anthropic's multi-agent orchestration work, the four-part subagent contract and effort scaling; and from the reward-hacking literature, that a verifier the worker can edit is not a verifier — hence the frozen harness.

**Read `LEARNED.md` in this skill's directory before starting.** It contains distilled corrections from previous runs and overrides any conflicting default below.

## Workflow at a glance

- **Phase 0 — Initialize** (once, interactive): read the docs, ask the audit-loop count, confirm autonomy, **choose the run's worktree root**, detect greenfield/brownfield, confirm `.claude/settings.local.json` (permissions **and** git-guard) is in place (written before the session started for preference, **probed green either way**), `init`.
- **Phase 1 — Context** (every epoch): full codebase survey first (brownfield) or scaffold (greenfield); incremental map update from merges thereafter.
- **Phase 2 — Goals** (once): tickets seeded from the docs (or decomposed), machine-checkable metrics with numeric targets, acceptance tests written *before any implementation* → **CHECKPOINT: plan approval** → `freeze` → baseline → commit `.swarm-loop/`.
- **Phase 3 — Schedule**: compute the ready frontier (dependencies closed, blast radius clear); dispatch is rolling, waves are emergent.
- **Phase 4 — Dispatch**: one worktree + branch per ticket — at the run's worktree root, provisioned before the agent starts; probe the git-guard; spawn every ready, non-interfering ticket with a complete packet.
- **Phase 5 — Collect** (pipelined per returning branch): integrity, scope, test-diff audit, report triage; bug reports mint tickets.
- **Phase 6 — Integrate + verify**: merge one branch at a time through an integration branch, tests green after each; then main; **one adversarial verifier per integrated batch** (the ladder). **No push here** — the push is gated by Phase 7's measurement and fired at the end of Phase 8.
- **Phase 7 — Evaluate** (each measurement epoch, and only an epoch that landed at least one merge): `verify`, `measure`, `analyze`, `checkpoint` — regression verdicts and terminal signals; **the push gate is defined here and fires at the end of Phase 8**, because its last condition is Phase 8's ledger commit.
- **Phase 8 — Adapt**: reprioritize the frontier from the analysis (product loop); update the learnings file (process loop); sweep resolved escalations; write the epoch report; **commit `.swarm-loop/`**; **then run `push-gate` and push if configured**; loop to Phase 3 while tickets remain.
- **The build → audit transition**: when every ticket is closed and the metrics are green (or every red is explained — and a red whose explanation is that the goal itself is wrong is filed with `swarmloop.py escalate`), the build act ends.
- **Audit-fix loops (×N, user-set)** — four numbered steps per loop, so a `resume` can name a re-entry point inside one: **A1** audit the whole codebase in parallel, **A2** mint tickets from findings, **A3** resolve them through Phases 3–8, **A4** close the loop (`audit-loop-done`). A loop that mints nothing ends the run early via Phase 9.
- **Phase 9 — Prune** (only after a clean audit loop): propose removals, have a
  DIFFERENT agent try to prove each is alive, then approve personally. Uncertain ⇒ keep.
- **Termination**: final report with full metric trajectories; distill learnings into `LEARNED.md`.
- **Every user-facing turn ends with the open-asks block** — `swarmloop.py escalate --open-asks`, which is silent when nothing is waiting on the user, so it costs nothing to run unconditionally. Not a phase: it is an invariant, below.

## Three terms, defined mechanically (each of them gates behaviour)

- **Measurement epoch** = one pass of Phases 3→8 that ends in a single `measure --cycle N` / `analyze --cycle N` / `checkpoint --cycle N` triple. **Epoch number *is* cycle number** — one epoch, one cycle, one row per metric in `history.csv`. The epoch opens when the first ticket of that pass dispatches and closes when `checkpoint --cycle N` records HEAD. Because dispatch is rolling, one epoch's merges and the next epoch's builds overlap freely; the one thing that may never overlap is the measurement itself, which runs against a settled `main`. **An epoch that landed no merges is not an epoch and must not be opened** — see the Phase 7 stall rule, which is the difference between a healthy wide swarm and a kill-switch termination.
- **Merge-review bandwidth** = how many accepted-but-unmerged branches the orchestrator is currently carrying. The mechanical rule: **stop dispatching new *mutating* tickets while more than 5 returned branches are waiting on collection or integration, and resume when that queue is back to 3 or fewer.** That is the only throttle on dispatch — width is otherwise bounded by blast-radius interference, never by a headcount — and read-only agents (recon, verifiers, auditors, delegated readers) are never counted in it at all, because they cost no merge review. The "3–5 per *integration batch*" figure in Phase 3 is a batching heuristic for the merge itself, not a cap on how many agents may be running.
- **Autonomy mode** (`init --autonomy <mode>`, exactly three values):

| Mode | Plan checkpoint (Phase 2) | Approval before dispatching the next epoch's frontier | Route pivots, scheduling, hotfix dispatch, merges, measurement, push gate |
|---|---|---|---|
| `approve-cycle-1` (default) | required | no | autonomous |
| `approve-every-cycle` | required | **required** — present the epoch report and *stop*; the Phase 8 "close the loop with a tool call" rule is suspended for this mode, and the next dispatch waits for the user | autonomous |
| `fully-autonomous` | not required | no | autonomous |

  No mode authorizes changing a frozen artifact. `freeze --amend` is the user's call, made awake, in all three.

## Invariants (why the loop can be trusted)

- **Goals are frozen after the plan checkpoint — the freeze is a locked door, not a wall.** The whole point is measuring error against a fixed target. A goalpost that moves each cycle makes the regression meaningless and invites the failure mode where the system "succeeds" by redefining success — so the lock is mechanical and it holds. But "frozen" has never meant "wrong forever, do not touch under any circumstances." It means **the artifact cannot change without the user, and a frozen thing that turns out to be wrong must be carried to the user, loudly and unmissably, with a specific proposed change.**
- **Three levels of the frozen boundary — they must never blur into each other.** **Workers: a hard wall.** A worker never touches anything frozen, for any reason, however good the reason looks from inside its worktree; it reports the objection through its packet's `NEEDS` channel and keeps building everything else. The mechanical `check-branch` veto is unchanged — a branch touching a protected path is rejected every time, with no appeal at the worker's level — and that asymmetry is the anti-gaming property the whole harness rests on. A real channel for a legitimate objection makes that wall *easier* to hold, not weaker: the worker no longer has to choose between silence and tampering. **Orchestrator: a permission boundary.** When the orchestrator concludes a frozen artifact is genuinely wrong, its one obligation is to **escalate** — `swarmloop.py escalate --kind <frozen-goal|frozen-test|harness|blocked-ticket|other> --subject "<metric id / file path / ticket>" --reason "<why, with evidence>" --proposed "<the specific change requested>" [--blocking] [--cycle N]`, which appends to the append-only `.swarm-loop/escalations.jsonl` and mirrors the human-readable `.swarm-loop/ESCALATIONS.md`. Never work around it, never quietly re-freeze it, never keep scoring against a target you believe is broken while saying nothing. **Escalating is asking, never granting.** The orchestrator does not acquire permission by having a strong case, by the user being asleep, by the run stalling, or by filing the escalation and waiting a while: filing it changes nothing except that a human can now see the problem, and that is exactly what keeps this reframe from becoming a goalpost-moving hole. **User: the only one who can authorize.** `freeze --amend "<reason>"` remains the only thing that actually changes a frozen artifact, it is the user's call made awake, and it is logged.
- **An ask nobody sees is an ask nobody filed — every user-facing turn ends with the open-asks block.** Filing the escalation is half the obligation; surfacing it until it is answered is the other half, and the hole is the **non-blocking** ask — the common case, designed to keep the run moving (file it, then keep pivoting the route and keep building everything the dispute does not touch). So the question gets a durable home on disk and no path to the eyes of the one person allowed to answer it, while hours of output scroll past it. That is this skill's recurring defect class exactly: a mechanism that looks like it is doing its job with no path by which it can fire. The fix is mechanical, not aspirational — **end every turn the user will read with `python3 <skill>/scripts/swarmloop.py escalate --open-asks`.** It prints every open ask, newest first and blocking on top, each with what was asked, about what, the specific change proposed, when it was filed, and the one command that closes it — and it prints **nothing at all, exit 0, when none are open**, which is the property that makes running it unconditionally possible (a block that says "nothing is waiting" two hundred times trains the eye to skip the block, and then the one turn carrying a real question scrolls past with the rest). Exit **2** means a blocking ask is open: the run is **waiting on a human** — neither done nor failed, and never to be reported as either. **Corollary, and the half that will actually get violated: an ask that was never filed as an escalation does not exist.** A question typed into the chat and then buried under an hour of output is not an ask, it is a thought; if the orchestrator wants an answer it files one, so the question outlives the scrollback and comes back every turn until it is answered. This repo learned that lesson once already, when HIGH-severity findings lived only in session context and died with the session. **Closing an ask keeps the same asymmetry.** `escalate --resolve <ID> --note "<what the user decided>"` records a decision the *user* made, and the note is mandatory — an ask closed with no recorded decision cannot be told apart from a loop retiring its own inconvenient question. A question that genuinely became moot (the route pivoted, the ticket was dropped) is `escalate --withdraw <ID> --note "<why>"`, which is recorded permanently as NEVER ANSWERED and is **refused outright for a blocking ask** — that one stopped the run to wait for a person, and the loop does not get to answer it by closing it.
- **The freeze mechanics, unchanged.** `swarmloop.py freeze` hashes `goals.json`, the acceptance tests, and — when the run has one — **the ticket graph**, because `red-check` reads `bootstrap` off a ticket and an unhashed input to a gate is a gate a worker can edit around. The graph is protected the way the acceptance suite is: tamper-EVIDENT, not blocked. The orchestrator amends it legitimately and often, so `freeze --amend` prints its old→new hash, and `findings` re-seals exactly that path when it mints — refusing outright if the graph already disagrees with the manifest, which is what stops the mint becoming the laundry; `verify` must pass before every scoring; a branch that touches protected paths is vetoed at merge time by `check-branch`. If verification ever fails, run `swarmloop.py restore-harness` — it rewrites every protected file back to its frozen bytes, sourced from git by manifest digest. A file *added* under a protected path after the freeze is only reported (`[ADDED]`), never deleted: `restore-harness` exits 1 while any remains and `verify` keeps failing, so read each one and then re-run `restore-harness --remove-added` to delete them — deliberately a second, explicit command, because deleting an unrecognized file under the harness is not something to do by reflex. Do **not** re-run `freeze` to clear a violation: that re-locks the tampered bytes and silently moves the goalposts. A violation you genuinely cannot restore is `escalate --kind harness --blocking` — scores are void until a human rules, and re-freezing to make the red go away is the one repair that destroys the evidence of what happened. `freeze` refuses to run over an already-frozen harness without `--amend "<reason>"`, and an amend prints the old→new hashes and diffs and appends an append-only record to `.swarm-loop/freeze-log.jsonl` that every later `analyze`, `resume`, `status`, and the final report surfaces. **A mid-run re-freeze is a USER-AWAKE action** — never an orchestrator's or a worker's call, and never a repair for a red `verify` or a red metric. Note that `git checkout -- <path>`, `git restore <path>` and `git checkout HEAD -- <dir>` are all blocked by this skill's own git-guard, for everyone, the orchestrator included; `restore-harness` is the sanctioned equivalent (the manual one is `git show HEAD:<path> > <path>`). Scores against a modified harness are void.
- **Goals are frozen; the route is not.** How a thing gets built — the design, the decomposition, the implementation approach, the plan sketched in a task packet — may change at any moment, mid-task and mid-cycle, without user input, whenever evidence says the current path is wrong. Pivoting the route is not renegotiating the goals, and confusing the two freezes is how a loop wastes cycles being timid. What stays frozen without the user: the goals, the acceptance tests, the packet boundaries (ownership, dependencies, `.swarm-loop/`), and existing assertions absent the recorded `justify-test-edit` ritual. Workers pivot freely inside their ownership (see the "Your discretion" tier in `references/task-packets.md`); the orchestrator pivots decomposition, scheduling, and approach at any moment. Stopping to ask is for boundary crossings and goal changes — never for route changes. And "asking" is `escalate`, which is not a stop: file it, then keep pivoting the route and keep building everything the dispute does not touch. Only a genuinely blocking escalation halts the run.
- **A metric is only as frozen as the files it reads.** `freeze` hashes `goals.json` and `.swarm-loop/acceptance/`; it does not hash the repo's test configuration, and a metric command inherits whatever config the tree happens to hold at measure time. Reproduced: a worker drove a frozen acceptance metric from 50 to 100 with a two-line `pyproject.toml` (`addopts = "--ignore=<the failing tests>"`) — `check-branch` passed it (pyproject.toml is not a protected path), the `'*test*'` diff audit passed it (it does not match the glob), and `verify` passed it (not one frozen byte moved). **A metric whose result depends on any file outside the frozen manifest is not a frozen metric.** So metric commands pin their own configuration rather than inherit the repo's, and any config surface a command still reads joins `protected_paths` at freeze time; the wrapper rules and the per-stack list of config surfaces are in `references/goal-setting.md`, to be read before a single `command` is written. The same principle bites from the other side: a command that *walks* the tree from the repo root also walks whatever the run has parked inside the repo — **a metric whose value moves when a worker is dispatched is measuring the swarm, not the product.**
- **A FORGEABLE shortcut in the measuring apparatus buys nothing — and this one is a closed question, not an open design space.** The tempting shortcut is caching: run the suite once, write a report artifact, and have the twelve metric commands read *that* rather than each re-running the suite. It was built; then **two independent verifiers drove both the pass-rate metric and its companion count to target from a ONE-LINE, worker-written JSON file, while `verify` reported the harness intact throughout** — not one frozen byte had moved. Hashing the frozen directory into the report does not close it: workers read that directory and compute whatever hash they must match. Measured cost of honesty — **and read the SCALE printed beside the number, because one of these figures has talked orchestrators out of the escape hatch below.** On a toy suite: eleven runner invocations 9.2 s, the full check 8 s, the whole twelve-metric sweep ~17 s. On a real one it is nothing like that. Where the acceptance runner executes the ENTIRE suite and filters by epic *afterwards*, and twelve of thirteen metrics shell to it, a 3090-test suite at 324 s makes that same sweep roughly **65 minutes**, and the run's own watchdog computed a worst case near **six hours** under the per-command caps. An orchestrator reading "~17 s" never reaches this invariant's escape hatch, because at 17 s the cost never looks like it needs one. The shortcut still bought nothing at either scale. **Every metric re-runs its own command, every measurement; do not re-propose report reuse or any memoized artifact standing between a metric and the thing it measures.** **And when a sweep is genuinely too slow, the first remedy is neither caching nor fewer metrics: a metric command should SELECT ONLY WHAT IT GRADES.** Twelve metrics that each run the whole suite and filter afterwards are eleven wasted full runs — that is where the 65 minutes above came from, not from honesty. Per-metric selection at the runner (`-k` / `-m` / a path or epic argument, whatever the stack's selector is) shares nothing, memoizes nothing, and leaves nothing worker-writable between a metric and its measurement: every metric still runs its own command, it just stops running twelve times the work it needs. Selection is decided when the metric's command is *authored*, not at measure time — so it belongs in `references/goal-setting.md` beside the config-pinning wrapper rules the invariant above cites, and a command written to grade an epic by running everything and filtering is a defect to fix there rather than a sweep to endure here. Only when selection genuinely cannot narrow a metric is the answer fewer or cheaper metrics — and never, at any sweep duration, a cached number a worker can write.
- **Everything is a ticket, and `swarmloop.py findings` is how a finding becomes one — do not hand-roll it.** Build-doc tickets, workers' `BUGS-OBSERVED` reports, wave-verifier findings, audit-loop findings, red-metric fixes — one backlog, one scheduler, one lifecycle: minted → scheduled by readiness and blast radius → built → verified → closed. If work is happening that no ticket names, the orchestrator has lost the plot: mint the ticket first. **Pipe structured checker output (`severity`, `location`, `defect`, `reproduction`) into `swarmloop.py findings` rather than writing a formatting loop in-session.** It records every finding at every severity to `.swarm-loop/findings.jsonl` *before* any threshold is applied, then mints tickets at or above `--min-severity`, and prints the reconciliation — minted + below-threshold + already-ticketed must equal recorded, or it refuses. Measured, and this is why it exists: five checkers returned six HIGH defects; the MEDIUMs became tickets and the **HIGHs reached no repo artifact at all**, surviving only in a subagent journal — the severity filter was in effect inverted. The same in-session loop did `location.split('/')[-1]`, so four of eight tickets pointed at a file that does not contain the defect; a ticket naming the wrong file is worse than none, because it sends a worker to read code that is fine. `findings` carries `location` and `reproduction` verbatim, derives `scope` from the full path, and gives each minted ticket a `verify` placeholder that **red-check refuses** — so a finding-ticket cannot dispatch until someone writes a gate that fails on it. This is also what makes the run resumable and auditable — and **which artifact IS the ledger depends on the intake; getting that backwards is how two ticket graphs silently drift apart.** Greenfield or plain-description intake: there is no external graph, so `backlog.md` is the ledger and the ground truth, full stop. **Build-docs intake: the doc set's machine-readable task graph is authoritative and `backlog.md` is its human view.** Measured: an amendment added two tickets to the graph while the ledger still reported the old count in three places and named neither ID — and `resume` printed `harness intact` over it, because the harness never reads the graph at all. So, orchestrator's job, both of them: **reconcile the two at every `resume` and every freeze** (re-derive count, edges, roots and frontier from the graph, diff against the ledger's IDs and stated counts, treat a divergence as a loud failure), and **any amendment touching the graph must RE-SEED the ledger** — seeding is one-way, and nothing re-seeds it, so from the first amendment on the human view is stale in exactly the way nobody checks.
- **Subagents build; the orchestrator measures, merges, and decides.** Workers never run the scoring, never edit anything under `.swarm-loop/`, and never merge their own branches. Separation of builder and verifier is the anti-gaming defense that survives even a well-intentioned agent "fixing" a test to match its code.
- **Tests are append-only by default — the frozen harness is not the only verifier.** Freezing `.swarm-loop/acceptance/` protects the *goals*, but a worker's ordinary unit tests are just as load-bearing and fully editable, so the same "make the red thing green" pressure lands there instead. Adding a test or an assertion is free. **Modifying or deleting an existing assertion requires the `justify-test-edit` ritual** — quote the assertion, cite the requirement it encodes, and answer the discriminating question: *would this test still be wrong if I reverted my change?* If no, the code is wrong, not the test. Every disguise counts as modification — Phase 5 step 4 enumerates them and is where the audit happens. A test edit with no recorded justification is indistinguishable from reward hacking after the fact — so the justification lives in the diff and the commit body, and the orchestrator audits every test diff at collection.
- **A green metric is evidence about the metric.** The frozen harness measures what its
  acceptance tests exercise — which is usually a stub, a fixture, or the code called the
  way the test calls it. It cannot see a feature that is built-but-unreachable, a gate that
  grades a fixture instead of the system, a real dependency whose output shape differs from
  the recording, or a deployed image missing a file the code opens at runtime. All of those
  have shipped at 12/12 green. Before believing a cycle's numbers mean the product works,
  load the **`stub-blindness`** skill and exercise the real path once. 12/12 means "built",
  never "delivered".
- **Every number comes from `scripts/swarmloop.py`.** Never eyeball a trend or hand-compute a slope — the script's output is the single source of truth for verdicts, projections, the stall counter, and termination signals.
- **File ownership is mapped before dispatch, not discovered at merge.** Tickets that need the same files are serialized by the scheduler, never in flight together. This single planning step prevents most merge pain.
- **Keep the swarm saturated — gates are checkpoints, not a metronome.** Every moment where no agent is running and no integration is proceeding is waste. The gates in this skill exist to catch defects, never to set the pace, and none of them requires idleness: *mutating* concurrency is bounded by blast-radius interference rather than by a headcount (mutating agents run as wide as non-interference allows), while read-only agents run concurrently with everything **up to the Phase-3 fan-out budget**; collection is pipelined per returning branch, not batched behind the last straggler; the next wave's recon, packet drafting, and non-interfering dependency-free dispatches overlap the current wave's build and merge. Slowness is not caution — an orchestrator that leaves the swarm idle to feel careful is spending wall-clock without buying any verification.
- **Read bounded, or delegate the read — the orchestrator's context is the one resource the loop cannot regenerate.** Termination forbids ending a run for context pressure, so an orchestrator that reads whole files instead compacts *mid-epoch*, and a compacted orchestrator is the one that mis-reconciles the ledger or loses the epoch boundary. Three rules, all mechanical. **Never `cat` a file under `.swarm-loop/`** — the loop's own state is what `swarmloop.py status`, `resume` and `analyze` print, and a report is read with `tail -n 80 <file>`. **Bound every other read before you make it**: `wc -l` first, then `sed -n '<a>,<b>p'`, `head`/`tail`, `grep -n <pattern>`, and `--stat` before any diff. **Delegate any read over roughly 400 lines to a read-only subagent** whose brief names the *answer* you need — "return the open tickets", "return the learnings that apply to T-014", "return what changed in the map since <sha>", "return every removed assertion and whether it carries a justification" — never "read this file". Measured cost of not doing this: a mandated five-file reload of 3,203 lines blew the tool-output cap twice (61.1 KB and 33.2 KB spilled to disk) and forced three extra `sed -n` round-trips before any work started. Read-only subagents cost no merge review and run concurrently with everything, so there is never a throughput reason to read a large file yourself — but "no merge review" is the only cost they avoid. They still cost context, wall-clock, spend, and (if any of them provisions a tree) about a gigabyte of disk each. Delegate the read you actually need; the standing width cap is in Phase 3.
- **Every agent in a MUTATING wave runs in its own isolation — never a shared working tree.** Any wave whose agents write files gives each agent a dedicated git worktree (`git worktree add`, or the Agent tool's `isolation: 'worktree'`). A shared tree is unsafe not merely from file overlap (the ownership map handles that) but because a single *repo-global* git op — `git stash`, `reset --hard`, `checkout -- <path>`, `checkout .`, `clean -f` — reverts or deletes **every** agent's uncommitted work at once, across the whole tree. This is not hypothetical: a `git stash`+`pop` by one fix-agent silently reverted five siblings' in-progress edits mid-wave, and the pop then aborted on a conflict, stranding their work in a dangling stash. Read-only auditor waves (no branch, no writes) may share the tree; nothing that mutates ever may. The `PreToolUse` git-guard hook — a **Phase 0 precondition**, probed live at Phase 4 — is the backstop for when this rule is bypassed, but the isolation *is* the fix; the hook is only a bounded net under it.
- **The run is finite, and the ticket ledger is what bounds it.** The build act ends when the ticket set closes; the audit act ends at the user-set loop count or the first clean loop; **two** kill switches and the `--max-cycles` safety ceiling guard against a run that spins without closing tickets, and they ask different questions (both exit 2 from `checkpoint`). **The codebase switch** (`--stall-limit`, default 3) counts consecutive checkpoints whose product-tree fingerprint did not change — it measures **the product tree**, never the swarm's activity, so Phase 7's rule against opening a merge-less epoch is what keeps it from ending a healthy run. **The goal-progress switch** (`--goal-stall-limit`, default: the same number) counts consecutive **measured** cycles in which **not one graded metric's error fell**. That second one exists because the first structurally cannot see a stalled run: a loop that writes a line of product code every cycle resets the fingerprint counter forever, and a metric pinned at one value for seven straight cycles sat at stall 0/3 with 95 cycles of budget left. Any single metric improving resets it, a first-ever reading counts as movement, all-targets-met resets it, and a cycle that measured nothing **holds** it where it is — so a broken metric command is never what ends a run. An **open blocking escalation** (`escalate --blocking`, exit 2) is terminal in the same class, and it is its own state: the run is *waiting on a human*, which is neither "done" nor "failed" and must never be reported as either. Never talk yourself into "one more loop" past a terminal signal — and never end early for a reason no signal names (context pressure included).
- **Audit coverage is whole-project every loop — never partitioned across loops.** Build-act scheduling runs a prioritized frontier, because each feature is built once. That logic must never leak into the audit act: when the job is finding defects, **every loop re-sweeps the entire codebase.** Fan auditors out in parallel, but only if their union covers everything and the partitions rotate and overlap across loops, so no region is ever examined by one set of eyes on one loop only. Every auditor returns a coverage map; named gaps become mandatory targets. The redundancy is not waste — it *is* the guarantee that nothing was missed. Auditing stops only when a whole-project loop comes back with nothing worth fixing (the Phase 9 gate), never when "each area has been touched once."

## Phase 0 — Initialize (once)

Read the project description first — and read it **bounded**, per the bounded-read invariant: this is call #1 of the run and a whole spec streamed into your own context is the most expensive read the loop ever makes. For a PDF, convert to a file rather than to stdout (`pdftotext <file> <file>.txt && wc -l <file>.txt`), then read it in `sed -n` sections; past ~400 lines, hand the `.txt` to a read-only subagent whose brief is "return the requirements, the success criteria with their numbers, the non-goals, and the *Open questions* section verbatim". Never `pdftotext <file> -`. If scanned, read pages visually, in batches. A markdown brief follows the same rule. **If the intake is a build-docs doc set** — `SPEC.md` → `DESIGN.md` → a task graph (`TASKS.md` or a task store), often with an `EXECUTION.md` header, produced by the desktop `build-docs` planning skill — the planning half is already done: follow **`references/build-docs-intake.md`** (tier→loop mapping, precedence, and the derive-don't-invent procedure for Phases 0–3). Two intake rules bind immediately: a non-empty *Open questions* section in SPEC.md stops everything until the user answers, and the doc set owns *what* to build while this skill owns *how* the build runs. Then, in one exchange, ask the user:

1. **How many audit-fix loops after the build?** Suggest 2 for a small scope, 3 as a sane default, 5 for a large or safety-critical one. The build act itself is not budgeted in cycles — it runs until the ticket set closes. `--max-cycles` still gets a value at `init`, but as a generous **runaway safety ceiling** (a sane default: 2× the ticket count + 3× the audit-loop count + 5), not a plan; the kill switch and the ticket ledger govern the real shape. Pass the loop count as `--audit-loops N`.
2. **Autonomy mode** — one of the three exact values in the autonomy table above: `approve-cycle-1` (the default: approve the plan, then fully autonomous), `approve-every-cycle`, or `fully-autonomous`. Confirm it explicitly and pass it verbatim as `--autonomy <mode>`; the table says which gate each mode opens, and `approve-every-cycle` in particular suspends Phase 8's close-the-loop-with-a-dispatch rule. Also confirm push behavior: default is push `main` to the remote **at the end of Phase 8, after that epoch's measurement and its ledger commit**, for each epoch whose integration is conflict-free and green and whose measurement cleared the Phase 7 push gate; `--push-remote never` keeps everything local. Nothing pushes at integration time. Credential-holding actions beyond `git push` to an already-configured remote (deploys, secrets, account changes) are never the loop's job.
3. **Where the run's worktrees will live — decided here, once, and passed as `--worktree-root <path>`.** The answer is **beside the measured repo, never inside it**: `../<repo>-worktrees/`. This is a Phase-0 decision and not Phase 4's, for two reasons. First, `measure` runs every frozen metric command with cwd = the repo root, so a worktree parked under the repo sits inside every root-walking command's search path while holding a full source copy in a partial, mid-edit, deliberately-red state — and because this skill keeps dispatching while integration proceeds, the number of live worktrees at measurement time is unbounded and varies epoch to epoch. Measured: a file-count metric read **1** with no worktrees, **4** with three unprovisioned ones, and **10** once those were provisioned, which `analyze` reports as `regressing` with no product code having changed, and Phase 8 then spends an epoch diff-hunting a product cause for orchestration noise. Second, `resume` matches live worktrees against the run's *configured* `worktree_root`, so a location chosen ad hoc at dispatch time makes a resumed session report **zero** live worktrees and re-dispatch every in-flight ticket into a second set. If the repo's parent directory is not writable, an in-tree location is the fallback — and then the worktree-exclusion half of Phase 2 step 3 stops being belt-and-braces and becomes the only defense. Either way, one location for the whole run, written into `init`, into every packet, into Phase 5's teardown command and into the merge protocol's cleanup step.

Detect the codebase situation: inspect the working directory for `.git/`, dependency manifests, a populated `src/`. Brownfield if a real project exists; greenfield otherwise — say what you found and let the user correct you.

Also check for a **`.codegraph/` index** at the repo root. If present, CodeGraph is the run's default codebase navigation **in the primary checkout — the orchestrator's tool, not every packet's** (Phase 1, Phase 9, and any read-only verifier that is actually standing in the primary tree). If absent, ask the user once in the same init exchange whether to index first — indexing is the user's decision, and without an index CodeGraph is skipped entirely for the run. **It is NOT available to Phase 4 workers, and it is unavailable in the dangerous way: `.codegraph/` is gitignored, so `git worktree add` never carries it, and a query issued from inside a worktree does not fail — it walks UP and answers from whatever index it finds above.** Measured on a live run's tree: `.codegraph/` gitignored at line 38, present in the primary checkout, absent from all 8 worktrees, and the upward search from one of them resolved to `<repo-parent>/.codegraph` — an index holding 7,946 files across 9 unrelated projects and **zero** files of the project being built. The run's own orchestrator measured the same query both ways: from the primary checkout, 48 symbols across 3 files correctly naming the project's module and its 11 callers; from a worktree, 25 symbols in 1 file of a third-party library's internals, none of it this project. One lane noticed and fell back to direct reads; a lane that did not would act on another codebase's symbols with nothing indicating anything had gone wrong. **State the general rule, because the next such tool will not be called CodeGraph: any capability that lives in a gitignored directory is absent inside a worktree, and the ones that answer anyway instead of failing loudly are the expensive ones.** A worker packet says: use `git grep` and direct reads; if you run an index CLI at all, verify every path it returns is inside your own tree before believing a word of it.

Also check whether a Jira/Atlassian MCP server is connected. If so, confirm the mirror in the same exchange (on by default; project key to use or create) and follow the setup in **`references/jira-mirror.md`** — a scrum board per project, sprints per cycle, issues per task, moving in real time as the loop runs. If no Jira MCP is connected, skip silently; the loop is identical without it. Then:

```bash
python3 <skill>/scripts/swarmloop.py init --max-cycles <ceiling> --audit-loops <N> \
    --autonomy <approve-cycle-1|approve-every-cycle|fully-autonomous> \
    --push-remote <when-clean|never> \
    --worktree-root ../<repo>-worktrees \
    --stall-limit 3
    --goal-stall-limit 3
```

Every flag that shapes the run is on that line (`--project` and `--force` are the only others), and the last two are the ones runs forget. **`--worktree-root`** records the Phase-0 location decision above so `resume` can find live worktrees; omit it and `resume` looks under `.swarm-loop/worktrees` instead, finds nothing, and re-dispatches in-flight tickets. **`--stall-limit N`** (default 3) is how many consecutive checkpoints with an unchanged product-tree fingerprint trip the codebase kill switch — raise it only with a stated reason, and never as a substitute for Phase 7's rule against opening an epoch that landed no merges. **`--goal-stall-limit N`** (defaults to `--stall-limit`) is the other switch: how many consecutive **measured** cycles may pass with no improvement in any graded metric. Raise it only for a build whose metrics are genuinely expected to sit flat through a long scaffolding stretch, and say so in the cycle report when you do — the whole point of the number is that a run which is not moving its goals gets stopped and reported rather than quietly spending its ceiling.

Greenfield with no repo yet: `git init -b main`, commit a baseline, then `init`. Re-running `init --force` on top of a prior run archives that run's `history.csv` and `analysis/` into `.swarm-loop/archive/run-<timestamp>/` (gitignored) so the regression never mixes two runs' data.

**`.claude/settings.local.json` is a precondition of the run, not a step inside it — write it before the `claude` session for this run is launched.** One file does two jobs: the project's gitignored `.claude/settings.local.json` carries the run's permission allowlist *and* the git-guard `PreToolUse` hook entry (placement and precedence in Phase 4 below). **The reason for the precondition is no longer that a late file cannot load — it is that a late file is not PROVEN to have loaded.** This file used to assert that a settings file created after session start is never picked up, measured against Claude Code 2.1.252. **Re-measured against Claude Code 2.1.259, that is false in both halves.** Permissions evaluate live: a `deny` added mid-session by an external process takes effect on the next tool call. *Hooks load live too* — a `.claude/settings.local.json` (or `settings.json`) created mid-session by an external process fires its `PreToolUse` hook on the very next Bash call, in headless and interactive sessions alike and in subagents dispatched afterward; editing a file that was already there swaps the hook just as live, the old entry gone rather than merged. Only the **tool list** is frozen at startup, which is why a bare `"Write"` in `deny` *at session start* removes the tool from context outright (*"No such tool available: Write"*) while the same rule added mid-session leaves the tool listed and refuses the call at the permission layer — both block, by different mechanisms. Note that the official settings documentation still says the opposite for hooks (*"changes take effect only when a new session starts"*), so treat this as the observed behavior of one version rather than a contract. **So a guard installed once the run is under way is not the measurable no-op this file used to claim — it is an unverified guard, a smaller problem with the same remedy.** If you find mid-session that the file was missing: write it, then re-run Phase 4's two-call probe, because a green probe is the only thing that makes the guard live *in fact* rather than in belief — and that probe, not the file's timestamp, is what the precondition was really buying. If it does not go green, escalate blocking and stop rather than dispatching. What does not change is the cost already paid: everything the session did before the file appeared ran unguarded and un-allowlisted, and that banked window is why the file goes in first and why the escalation stays. The permissions half matters for the same reason: in an unattended run, a permission prompt is a hung worker misdiagnosed as a failed task. Enumerate what this build will touch and dry-probe one call of each kind before wave 1. Template, checklist, the full measurement, and the browser's second (extension-level) gate: **`references/run-permissions.md`**.

**Read every version stamp in this skill as an expiry date, not a credential — that is the real lesson here.** The claim above was measured, stamped `2.1.252`, correct when written, and silently false by `2.1.259`; nothing announced the change, no test caught it, and it went on justifying a precondition for however many versions it took someone to re-probe. A stamped measurement that rots is recoverable because the stamp tells you what to re-run; an unstamped one is not. So stamp what you measure, and when a stamp names a version you are not running, **re-probe rather than quote.**

## Phase 1 — Context (first entry in full; map upkeep every epoch)

The map lives at `.swarm-loop/codebase-map.md` and is what task packets quote from, so keep it accurate and compact — components, entry points, data model, conventions, test layout, known hazards (hotspot files everyone touches, fragile modules).

- **First entry, brownfield:** do a genuine onboarding, not a skim — README/docs, dependency manifests, directory shape, entry points, schema, integrations, existing tests (tests reveal intended behavior). Use parallel read-only subagents for any survey larger than a few files — one per area, within the standing read-only width cap in Phase 3, since read-only work costs no merge review (and nothing else it costs is free). Write the map.
- **Navigate with CodeGraph when indexed — in the primary checkout, which is where this phase runs.** `codegraph explore "<question or symbol names>"` (or the codegraph MCP tool) returns verbatim line-numbered source plus the call paths between symbols and a blast-radius summary in one query — including dynamic-dispatch hops grep can't follow. Reach for it before grep/find or bulk file-reading, for the initial survey and for every incremental map update. A direct CodeGraph answer is one to a few calls; a grep/read exploration of the same question is dozens. This is orchestrator navigation and the index is genuinely here; **a Phase 4 worker in a worktree has no index and must use `git grep` and direct reads** — and would get a confident answer about a different codebase if it tried (Phase 0).
- **First entry, greenfield:** scaffold the skeleton (structure, tooling, test runner, lint/type config, CI-style check script), commit, and write the map from what you created. **The scaffold is ticket T-0, and the orchestrator builds it here, in Phase 1 — it is never dispatched to a worker and never appears on a frontier.** It enters `backlog.md` in Phase 2 **already closed**, with the commit that created it named as its resolution; it is on the ledger so that later tickets can declare `depends_on: T-0` and so the run's history is complete, not because anything is owed on it. Without it the baseline metrics are not measurable at all.
- **Every later epoch (from Phase 8's loop):** don't re-scan, and **don't do it yourself**. The inputs are bounded and mechanical: `tail -n 80 .swarm-loop/reports/cycle-<N-1>.md`, the epoch's merges (`git log --merges --oneline <previous epoch's HEAD>..main`, the HEAD taken from `state.json` → `head_history` — there is no "merge log" file, and nothing in this loop writes one), and `git diff --stat <that HEAD>..main`. Hand those three, plus the current map, to a read-only subagent whose brief is "return the map's changed sections, rewritten, plus anything in the diff the map contradicts" — the map update is a recurring whole-file read and belongs in a subagent by default. You apply its edits and keep the judgment. Note anything a subagent reported that contradicts the map.

## Phase 2 — Goals (once, before any building) · CHECKPOINT

This is the most consequential phase — everything downstream regresses against what you set here. Read **`references/goal-setting.md`** before writing anything; it covers metric design, the `goals.json` schema, and the anti-gaming rules in full.

**With a build-docs intake, derive — don't invent.** The ticket graph seeds `backlog.md` verbatim (T-IDs, dependencies, scopes, non-goals preserved; T-0 is the scaffold, built by the orchestrator in Phase 1 and entered already-closed) — **and re-seeds it on every amendment that changes the graph**, since the graph stays authoritative and the ledger is its human view; `goals.json` metrics come from SPEC success criteria and per-ticket acceptance counts, with R-ID/T-ID traceability; `acceptance/` is written from the tickets' acceptance criteria and DESIGN's verification strategy. Run the adversarial pass against the *codebase*, not just the prose — scope globs and delta-spec claims are claims until checked against the tree. Full procedure: `references/build-docs-intake.md`. The checkpoint then presents the docs' plan with every intake divergence flagged, rather than a re-derivation. **And the graph is FROZEN with the harness: `freeze` adds it to `protected_paths` and hashes it, `verify` fails on a moved byte, `check-branch` vetoes any lane that touches it.** The reason is `bootstrap: true` — `red-check` reads that field from the graph to exempt a ticket from must-go-red, so the graph is **an input to a gate, and an unhashed input to a gate is a gate a worker can edit around**: a worker could add `bootstrap: true` to its own ticket and exempt itself from the check that would have caught its defect. The git-guard cannot close that — the canonical graph is repo-root `tickets.json`, outside `.swarm-loop/` entirely, where the ledger rule can never reach — so this is tamper-EVIDENCE, not prevention, exactly as for the frozen acceptance suite. **Amending the graph stays normal and expected; it just stops being silent**: `freeze --amend "<reason>"` prints the old -> new hash with a unified diff and records it in the append-only freeze log, and `swarmloop.py findings` re-seals its own mints the same way (a `graph-mint` record naming the ticket ids) so an audit loop never has to choose between minting tickets and a green `verify`. A run with no graph is unaffected — greenfield and plain-description intake never see any of this.

The short version:

1. **Decompose the description into atomic features** — each independently implementable, testable, and small enough for one subagent context. Record them in `.swarm-loop/backlog.md` with IDs, descriptions, dependencies, and the files each will own.
2. **Write acceptance tests first**, into `.swarm-loop/acceptance/`, before any implementation exists. Tests-as-goals is the mechanism that makes "error" measurable: a feature's completion metric is literally its passing test count. Expect them all to fail at **cycle 0** — that *is* the baseline (cycle 0 everywhere: `measure --cycle 0`, `state.json`, `goal-setting.md`; the "cycle-1" in `--autonomy approve-cycle-1` names the *plan checkpoint*, not a measurement).
3. **Define `goals.json`**: a handful of global metrics (acceptance pass rate, lint/type error count, build success, coverage if meaningful) plus per-feature metrics, each with a shell `command` that prints a bare number as its last stdout line, a numeric `target`, and a `direction`. 6–12 metrics total; more dilutes signal. **Write every command hermetically — a metric that reads a file outside the frozen manifest is not frozen** (see the `addopts` invariant above for what that costs). Two rules follow, and the freeze smoke-run is where you confirm both: **pin the command's own configuration** instead of inheriting the repo's, and put any config surface it still reads into `protected_paths`; and **exclude the worktree root and `.swarm-loop/` from anything that walks the tree** (`--ignore`, `-not -path`, explicit `testpaths`) — a linter, type-checker or coverage tool invoked at the repo root walks whatever the run parks there, which is the 1→4→10 file-count measurement in Phase 0 item 3. The commands are frozen at cycle 0, when no worktree exists, and cannot be edited afterward without breaking `verify`. Wrapper patterns per stack: `references/goal-setting.md`.
4. **Present the plan and get approval, then freeze, then baseline — in that order.** The checkpoint below comes first (goals freeze *after* the plan checkpoint, per the invariant). Then `swarmloop.py freeze` — it smoke-runs every metric command first (same 2400s-per-command timeout as `measure`; `--smoke-timeout` adjusts, and a metric may carry its own `"timeout"`), and a command that cannot print a parseable number fails the freeze loudly (fix the command *before* anything is hashed; `--skip-smoke` bypasses, not recommended). Then the cycle-0 baseline: `verify`, `measure --cycle 0`, `checkpoint --cycle 0` (the checkpoint seeds the kill switch's HEAD history). **Then commit `.swarm-loop/` to `main`** — goals.json, acceptance/, manifest.json, state — **and the dependency lockfile every worktree's clean install will need** (`package-lock.json` / `pnpm-lock.yaml` / `yarn.lock` / `uv.lock`) — **before any dispatch.** Worktrees see only committed state: an uncommitted harness means every wave-1 worker's "Done means" points at acceptance tests that do not exist in its tree, and restoring a violated harness from git requires exactly this freeze-time commit. **This is the first of the run's `.swarm-loop/` commits, not the only one** — every epoch boundary commits it again (Phase 8), or the epoch push — Phase 7's gate, fired at the end of Phase 8 — ships a `main` carrying none of the run's evidence.

**Checkpoint:** present the ticket graph, the metrics with targets, the audit-loop count, and the initial frontier the scheduler derived. Get explicit approval (per the autonomy mode) before dispatching anything. After approval the goals do not change without the user, and the one distinction to carry for the rest of the run is that **wrong is not the same as hard**: hard is the job, and a metric that refuses to move is ordinary Phase 8 steering, never a broken goal. A goal mid-run evidence shows to be genuinely *wrong* is `swarmloop.py escalate --kind frozen-goal --subject "<metric id>" --reason "<the evidence>" --proposed "<the exact change you are asking for>" --cycle N` — never a quiet renegotiation with yourself and never silence. Everything else about escalation — the three levels, asking-is-not-granting, non-blocking never stops the run, when `--blocking` is earned — is in the Invariants above; apply it, don't restate it.

## Phase 3 — Schedule the frontier

Waves are **computed, not planned**. From the ticket ledger, a ticket is **ready** when every `depends_on` is closed; a ready ticket **dispatches** the moment its blast radius overlaps no in-flight writer and merge-review bandwidth allows — bandwidth being the mechanical rule in the terms above: pause new *mutating* dispatch above 5 returned-but-unmerged branches, resume at 3 or fewer, and never count a read-only agent against it. The worked shape: six tickets where 2 waits on 1, 4 waits on 3, and 6 waits on 5 — the first frontier is {1, 3, 5}, all at once; {2, 4, 6} follow as their blockers clear. And *rolling*: if ticket 1 closes while 3 and 5 are still building, ticket 2 dispatches immediately — it waits for its blocker, never for a round. Analyze the blast radius of every ticket **once, up front, at intake** (scope globs plus the shared surfaces globs can't see — registries, schemas, route tables) and record overlaps as scheduling constraints; recompute readiness continuously as branches land. **`check-wave` prefers a ticket's `owns`/`owned_files` per-file map over its `scope` globs, and any agent WITHOUT a worktree must be recorded with `swarmloop.py dispatch --agent … --files …` or the wave check cannot see it** (`references/build-docs-intake.md` §B2; `references/task-packets.md`).

**Three computations, none of which may be done by eye:** (1) the **ready frontier** — the graph loaded, validated acyclic with no dangling dependencies, and the ready set printed with depth and transitive-`unblocks` counts, **against a closure source you supply**. Nothing in the harness reads a ticket status field, because the graph has none and deliberately so: ground truth is git, and a ticket is closed when its work has landed on `main`. So closure enters `frontier` through exactly three arguments — `--closed T-001,T-002` (the operator stating a fact), `--closed-from-merged` (a `task/*` branch merged into `--base` **for which something positively establishes that the lane carried work** — a dispatch-ledger record pinning a tip the branch has since moved past, or a tip that is *not* on `--base`'s first-parent history and so entered through the second parent of a merge; anything else is reported UNDETERMINED *by name* and stays open), and `--closed-from-ledger` (tickets carrying an `accepted` verdict from `dispatch --close --ticket T-nnn --verdict accepted|rejected` — the only one of the three that survives `retire`, which deletes the landed branch the other one reads). **`0 closed` is not a measurement**: with no source supplied every ticket reads open, the ready set degenerates to the graph's *roots*, and finished work sorts to the top of it — so `frontier` now says that unmissably instead of printing the number straight, and cites any already-landed `task/*` branch as evidence the run is past its first wave — *and reports separately, by count, any merged lane it could not classify*, so "no landed branch found" is never printed over a question it never answered. That line is the fix; the flags are the belt to it. Measured live: `108 ticket(s) · 0 closed · 27 READY · 81 blocked`, ranking `T-000 depth 0 unblocks 81 "Monorepo skeleton with green empty verify pipeline"` first — a ticket that had shipped long before — while the five tickets the orchestrator was in fact dispatching read `blocked` behind their permanently-open ancestors. The same graph with the 50 landed ids supplied reads `50 closed · 36 READY · 24 blocked` with the real work on top. **A frontier that ranks a ticket you know shipped is that defect, not a scheduling opinion**, and the direction is chosen accordingly: a false-CLOSED silently drops real work, a false-OPEN only burns a lane, **so anything unproven stays open**. Two predicates that look like they prove a lane was built do not, and both shipped as guards before being measured: `rev-list --count <base>..<branch> == 0` is true of a provisioned lane *and* of every properly merged branch, since "merged" means exactly "contributes nothing base lacks"; and `tip == <base tip>` is true of a provisioned lane *and* of a branch merged `--ff-only` — while being false for a provisioned lane the moment base takes any further commit, which in a swarm is continuously. Hence positive evidence only, and two limits to know: a lane merged fast-forward with no ledger record reads UNDETERMINED (record `dispatch --close … --ticket T-nnn --verdict accepted` and it closes), and `--merged` is **reachability, not presence** — `git revert -m 1` of a merge takes the work back out of `main` and leaves the branch listed as merged forever, so only a REJECTED ledger verdict reopens a reverted ticket. The ledger itself is a trust boundary with no read-side check: `--closed-from-ledger` honours an operator's record without re-deriving anything, and says so; (2) the **wave check** — refuse any candidate wave whose members' *ownership sets intersect*, naming the offending pair, and **read its fork accounting**: `check-wave` now pins the base sha the wave is about to fork from, and for any member that *already* has a branch it counts commits both ways. Neither count vetoes (pre-dispatch, a lane with zero commits is simply one that has been provisioned and not yet dispatched — the normal state), but a member whose branch forked from a base that has since moved **inside that ticket's own ownership** is about to be rebuilt against a tree that no longer exists, and the line naming those files is the one to act on: recreate the worktree from current base before dispatching. Live, seven lanes were dispatched onto worktrees 26–27 commits behind `main` and every one of them still merged clean, because textual mergeability is unaffected by a stale base; (3) the **red check** — run each candidate's declared `verify` in a clean tree and **fail any that already passes, and any that is not a real gate**: a non-zero exit is not enough, so WEAK (non-zero but zero tests *selected*), NO GATE and SKIPPED fail it too, and exit 0 means every selected ticket has a gate that actually ran tests and went red **or is a declared bootstrap ticket** (measured: all five of one wave's ticket gates were vacuous at dispatch — three exited 0 against nothing but scaffold smoke tests, and the two that reported `no tests ran` are exactly the case that used to exit 0 and now does not). **That exemption is that sentence's only exception, and it is data-driven and narrow:** it is claimed by a `bootstrap: true` field on a ticket and by nothing else — a bootstrap-*sounding* title without the field is still refused — it covers must-go-red and only must-go-red (a bootstrap ticket with no `verify` is still NO GATE and still fails the check, and its one attributed smoke test is still graded by freeze's coverage gate), and a graph declaring it on more than one ticket is refused outright rather than honoured. It exists for the graph's sole root, whose declared outcome genuinely *is* "pipeline green on an empty suite" and which would otherwise read VACUOUS or WEAK on the one ticket that must dispatch first. **Run all four and record the output** — `swarmloop.py frontier` *with a closure source*, `check-wave <ids…>`, `red-check`, and `reads` for the read-edge gate. They all exist; confirm against `--help` in the copy you are running, and never cite a subcommand you have not seen. **A subcommand that is missing is a harness defect to report, not a licence to compute by eye** — the sentence after this one names hand-derivation as exactly where the miss happens, and an opt-out clause here used to invite it. Hand-derivation in a per-wave throwaway heredoc is where the miss happens, and this is the one place a miss corrupts two branches at once.

**Priority within the frontier** follows the latest analysis: tickets touching regressing metrics first, then stalled, then converging-off-track; among those, the largest error contributions first. Before any analysis exists, order by dependency depth — unblock the most downstream work first.

For each ticket confirm atomicity before dispatch: one clear objective, done-condition tied to named acceptance tests, fits one subagent context, owns a specific file set. Split anything that fails the test — oversized tickets are the top historical cause of failed batches. Under a build-docs intake, validate `scope` globs against the real tree rather than taking them on faith — they were set at planning time against a repo that has since changed. **`parallel_safe` is an ADVISORY hint and never the dispatch predicate**: it is unusable in both directions (it marks safe pairs unsafe and unsafe pairs safe), and the predicate is per-file ownership. Record it, never dispatch on it; the ruling and its evidence are in `references/build-docs-intake.md`.

The **blast-radius map** (file ownership plus shared surfaces) governs concurrent dispatch:

- No two in-flight tickets share a file. Overlaps → serialized by the scheduler, or redesign one ticket to be additive-only (new file + import) instead of editing the shared file.
- Hotspot files (route tables, config, shared types, barrel exports) get one in-flight writer at a time. Dependency-manifest/lockfile changes get their own serialized ticket — never parallel.
- Wave width is bounded by **interference, not a headcount**. The rule: no two concurrent writers may share a blast radius — and blast radius means more than files (the ownership map's file lists are necessary, not sufficient): a shared registry, schema, route table, or global assumption two tasks both touch is the same collision wearing different files. Within that rule, run as many agents as the work offers. 3–5 mutating branches per *integration batch* sizes the batch, and is not a cap on how many agents may run — when tasks genuinely don't affect each other's work, go wider and split integration into more batches rather than idling agents. Read-only agents (recon, auditors, verifiers) run concurrently with mutating waves and cost no merge review — **but they are bounded, not uncapped, and "uncapped" is the word that cost this loop a user interruption.**

**The read-only fan-out budget (mechanical, and it binds every phase that fans out).** Rung 2 once overspawned to **54 agents across two workflows** and was stopped by the user, on a design of 14 finder lenses × *unbounded findings per lens* × 3 refuters each — one lens returning eight findings spawns twenty-four refuters by itself. "Read-only work costs no merge review" was the licence, and it is true about merge review and false about context, wall-clock, spend and disk. Four rules:

- **At most 8 concurrent read-only subagents.** State the planned width and the resulting total agent count *before* dispatching a fan-out, not after. Going above 8 is a decision, recorded in the epoch report with its reason — not a default.
- **Any fan-out whose width is a function of what an earlier stage FOUND is bounded in the pattern, not by judgment.** A per-finding dispatch is written `parallel(findings.filter(severityGate).slice(0, CAP).map(...))` — the `.slice()` and the severity filter live in the shape itself, because this pattern gets copied verbatim into the next workflow and whatever it copies is what runs.
- **Refutation is severity-gated:** 3 skeptics for a `critical` finding, 1 for a `high`, **orchestrator triage** for `medium` and `low` — three independent skeptics per low-severity docstring complaint is the exact waste this rule names. And cap findings-per-lens (10 is a sane default): past that, triage before refuting, never fan out on the raw list.
- **Log what the cap dropped.** A silent cap is its own defect — but bounding nothing at all is the *opposite* failure, not the safe one. Record, per lens, how many findings it returned, how many were refuted, and what was dropped unexamined, so the next epoch can see whether the cap is binding on real signal or on noise.

During the build act there is no separate review cadence: drift-hunting belongs to the **wave verifiers** (Phase 6, every integrated batch) and, after the build converges, to the **audit-fix loops** — where whole-codebase coverage rules live.

## Phase 4 — Dispatch the swarm

Per task: create the isolation, provision it, then spawn.

```bash
git worktree add <worktree-root>/<task-id> -b task/<task-id> main   # <worktree-root> = the --worktree-root chosen at Phase 0
cd <worktree-root>/<task-id> && <the project's own env-provisioning command>   # see below
```

**The location is not decided here — it was decided at Phase 0 item 3 and recorded in `--worktree-root`, and this phase just uses it.** Use `state.json`'s value, never an ad-hoc path: `resume` matches live worktrees against the configured root, and a path invented at dispatch time is a worktree a resumed session cannot see. Why it lives beside the repo rather than inside it is argued at Phase 0 item 3 and is not re-argued here.

**A worktree is version isolation, not environment isolation — provision the environment or the worktree is a lie.** A fresh worktree contains only *tracked* files, so every gitignored dependency or build directory (`node_modules/`, `.venv/`, `dist/`, generated clients) is missing. Measured, from a worktree nested at `<repo>/.swarm-loop/worktrees/<id>`: `require('@scope/pkg')` resolved to `<repo>/packages/pkg/index.js` — main's source, reached by the resolver walking UP out of the worktree and through the root `node_modules` workspace symlink — `npx` ran the primary tree's bin the same way, and `uv run --no-project` used `<repo>/.venv`, all while the worker's own edits sat untouched a directory away. Two failure shapes follow: the worker's edits look **inert**, so it burns the epoch chasing a change that was never loaded; or the branch goes **falsely green** on code that is not in its own diff (verified: an EMPTY branch diff passed the package's suite because the fix existed only in the primary tree — and once siblings start landing on `main`, that is the ordinary case, not a corner one). Placing worktrees beside the repo converts the silent wrong answer into a loud `MODULE_NOT_FOUND`, which is strictly better and still a blocked worker. So, for every mutating worktree, before spawning the agent:

1. **Provision inside the worktree, at dispatch, with the installer the committed lockfile selects** — run from the worktree root: `package-lock.json` → `npm ci`; `pnpm-lock.yaml` → `pnpm install --frozen-lockfile`; `yarn.lock` → `yarn install --immutable`; `uv.lock`/`pyproject.toml` → `uv sync`. **Select by lockfile, never by language.** A flat "always run `npm ci`" rule is a wave-1 outage: `npm ci` exits 1 with EUSAGE when no lockfile is committed (the greenfield case), when the lockfile is out of sync with `package.json`, on a pnpm repo, and on a Python-only repo. With no lockfile at all, `npm install` is the fallback — and it is a fallback, not the plan (see 3). Determine the command ONCE at intake (Phase 2) and paste it verbatim into every packet. **And assert the EFFECT, never the installer's exit code** — measured, `uv sync --frozen` **exits 0 against a changed manifest**, so a dependency addition becomes a silent no-op: command succeeded, environment does not match, nothing said so (`--locked` is the flag that fails loudly; `--frozen` is the more obvious one and is what the next author reaches for). Finish every provision by importing the module and printing its resolved path and version; the snippet is in `references/merge-protocol.md` step 8, which carries the same obligation for the primary measurement tree.
2. **Then run the project's build/codegen step** if any package's entry point is a gitignored artifact (`main: dist/index.js`, prisma/graphql clients). There is no universal incantation: `npm run build --if-present` silently skips workspace packages, and `npm run build --workspaces --if-present` exits 1 in a single-package repo. Use the command the project's CI uses.
3. **A committed lockfile is a freeze-time precondition, not a worker's problem.** It lands on `main` alongside `.swarm-loop/` at freeze (Phase 2 step 4). A worker that meets an EUSAGE by reaching for `npm install` writes a dependency manifest it is forbidden to touch, and N parallel workers writing N lockfiles is precisely the collision the serialized dependency ticket exists to prevent. If the stack has no lockfile yet, that IS a ticket — a serialized one, closed before the first mutating wave.
4. **Python under uv — a prohibition, not a preference.** `uv run <cmd>` from the worktree root self-provisions that worktree's own environment; it is the only sanctioned way a packet runs Python. **Never hand a worker an absolute path into the primary tree** — not `<repo>/.venv/bin/python`, not `<repo>/.venv/bin/pytest`, not `<repo>/node_modules/.bin/<x>`. Every command in a packet is written relative to the worktree root, and the packet clears inherited env that points home (`VIRTUAL_ENV`, `NODE_PATH`, `PYTHONPATH`).
5. **The provisioned directories must be ignored, or the worker commits them.** Verified: in a repo whose `.gitignore` omitted `node_modules`, provisioning plus the packet's own "commit your work" put nine dependency files on the branch and `check-branch` passed them — it vetoes protected and `.swarm-loop/` paths, and this is neither. Confirm the ignores before the first wave and put the provisioned paths on the packet's do-not-commit list.

**A provisioned worktree costs about a GIGABYTE, so the scaling law of fan-out is DISK, not context.** Measure it once per project and write the number into the run's notes; on the run this rule comes from it was **~1.0 GB** per tree (`.venv` 329 MB + `node_modules` 625 MB), and that is not a bug to fix — a correct bootstrap *refuses* to share a root venv, which is the whole point of provisioning. So fan-out multiplies as **agents × 1 GB**: eleven scratch trees took the worktree directory to **16 GB**, and the teardown `rm -rf` timed out at two minutes (exit 143). On a machine with 400 GB free that is survivable; on a fuller disk the same pattern fills it mid-run, and it surfaces as *unrelated tools breaking*, not as a workflow error. Four rules, all mechanical:

- **`df` before any fan-out that provisions trees.** `df -h .` and `du -sh <worktree-root>`, read the numbers, and refuse a fan-out whose worst case (planned trees × the measured per-tree cost) does not fit with room to spare. This is a pre-flight, not a post-mortem.
- **Cap concurrent PROVISIONED worktrees separately from concurrent agents.** They are different budgets — agents cost context and spend; trees cost disk and teardown time — and the read-only fan-out budget in Phase 3 does not bound trees at all.
- **Ask, explicitly, per lens: "does this need to EXECUTE?"** Most auditing lenses do not: a branch reads perfectly well through `git show <sha>:<path>` and `git diff` with **no tree at all**. Only sabotage and integration lenses need a bootstrapped worktree. Asking that question once would have cut eleven scratch trees to two or three, and it is the single highest-leverage line in this section.
- **Retire trees mechanically at each batch's verdicts — `swarmloop.py retire`, backgrounded, verified afterwards** — never inline, never in the critical path of the next dispatch. Procedure and path-safety: `references/merge-protocol.md` step 10.

**None of this is enforceable at `check-branch`** — it sees a diff, not a resolution path. Wrong resolution is *caught* only by rung 2's provenance duty (Phase 6), and *prevented* only here, at dispatch.

**Isolation is mandatory for every mutating wave — the single most important dispatch rule, and the one an orchestrator is most tempted to skip.** Each agent that will WRITE files gets its *own* isolation: the `git worktree add` above (one per task-id), or, when dispatching through the Agent tool, its own `isolation: 'worktree'`. **Never run a wave of file-mutating agents in the shared primary tree** — not even when the file-ownership map proves they touch disjoint files. The ownership map prevents *file* collisions; it does nothing against the *repo-global* git ops enumerated in the Invariants above, which revert or delete **every** agent's uncommitted work in that tree at once — the isolation invariant above carries the incident this rule exists to prevent. The only wave that may share the primary tree is a purely **read-only auditor** wave — no branch, no writes. If any agent in the wave will commit, the whole wave is isolated.

**The git-guard is a Phase 0 precondition — here you PROBE that it is live, you do not install it.** A settings file created mid-session **does** load on 2.1.259 — the "never loaded" claim this file used to carry was measured on 2.1.252 and has since rotted (Phase 0) — so a guard wired at this point is not automatically a no-op; it is merely *unproven*, and unproven is exactly what the probe below exists to settle. Give a freshly written entry no more credit than one that was there all along: the probe is the evidence, either way. The full procedure, the probed exit codes, the canonical `settings.local.json` template and the enumeration of what is blocked and what is deliberately allowed are all in `references/run-permissions.md` — **read them there.** Two hand-maintained copies is how the matcher drifted out of sync before, and this file used to carry a summary while telling you not to reason from it. What you need here: run the two-call probe (build a throwaway repo *with a commit*, then `git -C "$d" stash`), and **PASS is exactly one outcome — exit 2 with text containing `git-guard`.** Exit 0, `No local changes to save`, and git's own initial-commit error are each a FAIL: the command reached git, so the guard is not live and no mutating wave may dispatch. The guard **fails open** by design, so a fault allows the command and can never wedge the loop — which is exactly why its liveness must be probed rather than assumed.

**Precondition, not a suggestion: `check-wave <ids…>` must have exited 0 for exactly this set before anything spawns.** It is the only thing standing between two concurrent workers and the same file, `cmd_dispatch` does not and cannot enforce it, and a wave assembled by eye is where that miss happens. Its exit codes: **0** = no two members can own the same file and nothing in flight overlaps them; **1** = VETO (ownership intersects, a member overlaps in-flight work, no member declares ownership, or the graph contradicts itself) — split the wave or fix the graph, never dispatch past it; **3** = usage error. Then `red-check` on the same set, and only then spawn.

Spawn all subagents for a wave in parallel (one Task tool call each, same turn). A subagent only knows what its prompt contains — there is no shared context — so every packet must be complete. Use the template in **`references/task-packets.md`**; the non-negotiable contract is: objective + done-condition (named acceptance tests), output format (commits on its branch + a structured completion report, whose `BUGS-OBSERVED`, `NEEDS` and `CONFIG-TOUCHED` fields Phase 5 triages), boundaries (owned files; the prohibitions), and guidance (the relevant codebase-map excerpt + **only the learnings that apply to this ticket, never the whole `learnings.md`** — a packet that quotes the file wholesale multiplies a 30-entry process log by the width of the wave). The prohibitions every packet carries: never modify `.swarm-loop/` anything; never edit files outside your ownership; additive-only for shared surfaces; never touch dependency manifests or lockfiles unless the task *is* the dependency task (a failing install is a report, never a `npm install` you commit); never commit the worktree's provisioned environment (`node_modules/`, `.venv/`, `dist/`, generated clients) — that is the tree's plumbing, not the branch's work; run every command from the worktree root, never against an absolute path in the primary checkout; **never run a repo-global git op (`git stash`/`reset --hard`/`checkout -- <path>`/`checkout .`/`clean -f` — they clobber every parallel agent's tree; use read-only `git show HEAD:<file>` or `git diff HEAD -- <file>` instead);** **report every defect you notice, in or out of your scope — you may never FIX outside your ownership, but silence about a bug you saw is the only wrong move (the packet's `BUGS-OBSERVED` report field exists for exactly this); and if the thing you believe is wrong is FROZEN — a goal, an acceptance test, a protected path — you still may not touch it, ever, but you must say so in `NEEDS`: that report is the only route your objection has to a human, and the orchestrator is required to answer it or escalate it, never to bury it;** commit your work — uncommitted work is lost work; and **tests are append-only — add all you like, but do not modify or delete an existing assertion without the `justify-test-edit` ritual recorded in the diff and the commit body (a red test after your change means your code is wrong until proven otherwise; the orchestrator audits every test diff and rejects unjustified ones).**

## Phase 5 — Collect and check

Run these checks **per branch, as it returns — never batched behind the last straggler**. A wave's stragglers are drafting time: while they finish, check the returned branches, draft the next wave's packets, and update the map.

**Step zero, before check 1: PIN THE TIP.** Resolve `git rev-parse task/<id>` once, run every check below against that SHA, record it, and re-assert it before accepting — if the ref moved, the collection is void. A completion notification means "may still be moving", not "finished": three tips moved mid-wave in one run, one of them landing the fix for the branch's most serious blocker *between* the measurement and the acceptance. Procedure, evidence, and the per-ticket attribution query: `references/merge-protocol.md` steps 0–1 — read them before your first collection, because nothing else in the loop freezes a tip.

Before a branch is eligible for merge:

1. `swarmloop.py check-branch --branch task/<id>` — automatic veto on harness or orchestrator-state modifications, **and on a lane that delivered nothing**. It counts commits before it reads any diff: a branch with **zero commits of its own** vs the base is refused outright, because every other question the harness asks about a branch is ancestry-shaped and ancestry cannot count — an empty branch *is* an ancestor of `main`, merges clean, and reads MERGED everywhere else you look, so two lanes that were provisioned and never dispatched once passed every check and were counted as delivered work. A zero has two readings — the worker never committed (a failed or hung task: reclaim the ticket and re-dispatch) or the branch already landed and you are checking it after the merge — and the refusal is correct for both. It also reports, as an **advisory and never a veto**, how far the base has moved since the branch forked, with the files the drift and the branch have in common: a clean merge does not clear that, because the branch's own `verify` went green against a tree that has since changed. Rebase and re-run the verify before integrating when the overlap is real — and **an EMPTY intersection is not a clearance.** That line intersects the files that moved on the base with the files the lane owns, which is a statement about TEXT; the case it cannot see is a lane whose TESTS depend on semantics a sibling changed — a validation rule tightened, a default flipped, an error type swapped, a serialization narrowed — **in files the lane never touches.** Textual mergeability is unaffected by every one of those, so the merge is clean, the advisory stays silent, and the branch fails at runtime or, worse, passes a weaker assertion than the base now requires. When the intersection is empty, spend the second pass before clearing the lane: grep the lane's own directory for REFERENCES to the modules that moved on the base — imports, error types, constants, fixture factories — and read the base's diff for *behavioural* change rather than for moved paths (`references/merge-protocol.md` step 3). It also prints a third, **advisory** tag `?` beside any changed file a frozen metric's command may read (`pyproject.toml`, `setup.cfg`, `pytest.ini`, `tox.ini`, `jest.config.*`, eslint/tsconfig, coverage config, and the like). `?` is never a veto — it surfaces the one class of edit that can move a frozen number without touching a frozen byte, and no `?` merges unjustified. **But the `?` is computed here, after the worker has already written its report, so a branch that legitimately touches `pyproject.toml` / `package.json` / `Makefile` arrives with no justification through no fault of the worker's — do not read that absence as evasion.** Close it from both ends. Ahead of time: the packet's `CONFIG-TOUCHED` report field (`references/task-packets.md`) has the worker name any build/test-config file its ticket expects to change, and why, before it can know a `?` is coming. After the fact: any `?` the report does not already cover is a **question put back**, not a rejection — ask the worker if it is still live, or hand the file's diff hunk to a fresh read-only agent if it is not, and record the answer in the collection notes. An **unanswered** `?` blocks the merge exactly like an unjustified test edit; an *unjustified-because-unasked* one is your omission, not the branch's. **The veto is mechanical, it fires every time, and it is not the end of the question.** A vetoed branch goes back to the backlog as always — but read *why* the worker went there before you close the file on it. When the diff and the report show a **legitimate** reason to touch the frozen thing (an acceptance test that encodes a requirement the spec contradicts, a protected path the ticket demonstrably cannot be completed without, a frozen assertion the code proves is factually wrong), the rejection is only half the response: file `swarmloop.py escalate --kind frozen-test --subject "<the protected path>" --reason "<the worker's evidence, quoted>" --proposed "<what it should say instead>"` as well. A worker that found a real problem with a goal has done the run a service; burying that finding under a rejection is exactly how a wrong goal survives, unchallenged, all the way into the final report. Rejecting and escalating are not alternatives — the branch is still rejected, and the question the branch raised still reaches the user.
2. **Retro red-check: was this ticket's gate red immediately before this work landed?** `red-check` is named as mandatory in three places in this document and, until this step existed, was invoked by **nothing** — `grep -c cmd_red_check scripts/swarmloop.py` returned 2, the definition and the argparse line. What that cost, from the run's own `findings.jsonl`: **three tickets were reported closed twice with their defects live**, and red-check would have caught all three (VACUOUS for two, WEAK for one). Nobody ran it until cycle 10 and nothing required them to. So run it here, pointed at the branch's merge parent rather than at pre-build `main`:

   ```bash
   BASE=$(git merge-base main task/<id>)
   python3 <skill>/scripts/swarmloop.py red-check --close --ticket <id> --base "$BASE"
   python3 <skill>/scripts/swarmloop.py check-branch --branch task/<id> --base main --ticket <id>
   ```

   `--close` is what turns the **selection** findings from advisories into refusals. Those findings are the shapes that were measured being scored *"a real gate"*: **DESELECTED**, where the ticket's own frozen tests never ran (a `verify` of `pytest -q -m 'not slow' tests` against a slow-marked grading test — the red came from an *unrelated* broken test, and when a later ticket fixed that test the gate went **green with the defect fully live**); **MISSING**, where pytest cannot resolve the ticket's frozen node ids at that base at all (exit 4, `not found`); **collected NONE**, where pytest ran and selected nothing (exit 5); and **SWALLOWED**, where the count is read off the wrapper's own `echo` because the real run went to `/dev/null`. Two shapes are advisory in **both** modes and refuse nowhere: **FORCED** (`pytest tests/test_scaffold.py; exit 1` — passing tests, a red manufactured by the wrapper), because a wrapper whose red legitimately comes from a linter after a green pytest prints exactly the same thing — **read the command, the harness cannot tell those two apart and does not pretend to**; and **UNVERIFIED**, a collect-only run that hit a *collection error*, because the throwaway worktree has no venv and a missing third-party import is therefore the default for any project with dependencies. `SWALLOWED` is decided per shell segment, not over the whole string: `command -v jq >/dev/null 2>&1 || exit 3; pytest -q tests/t1.py` is a visible gate, and scoring it swallowed was a false refusal at merge that the printed remedy could not clear.

   **The stamp is written on both paths, so a selection finding at *dispatch* is not free.** `--close` changes the exit code, not the classification: without it red-check prints `red`, exits 0 and files the ticket under `red` — and stamps `swallowed`/`deselected` anyway, which `check-branch --ticket` later reads as a veto. That used to be silent; now the pre-dispatch run names every non-`red` stamp it wrote and says which branch it will refuse. **Fix the `verify` there, while nothing has been built against it** — re-running `red-check --close` over an unchanged command re-stamps the same verdict, so the veto clears only when the cause is gone.

   **`bootstrap: true`** on the graph's root ticket (build-docs emits it on T-0 only) exempts that one ticket from must-go-red: T-0's declared outcome *is* a green pipeline over an empty suite, so on a clean worktree its gate is VACUOUS or WEAK and red-check would otherwise exit 1 on the one ticket that must dispatch first. It is read from the ticket data and **never inferred from a title**, it exempts nothing else (a bootstrap ticket with no `verify` is still NO GATE, and still fails), and more than one `bootstrap: true` in a graph is refused — the contract is *true on T-0 only*, and a second one is either a mistake or someone widening the exemption to get a wave moving.

   Every red-check run stamps `{ticket, verdict, base_sha, cmd, timestamp}` into `.swarm-loop/redcheck.jsonl`, and `check-branch --ticket <id>` reads it — so this stops being a command someone has to remember and becomes a thing the merge gate asks for. That gate is **advisory for any ticket the ledger predates** (no ledger at all, or a ticket dispatched before its first stamp, or one `dispatch.jsonl` cannot date) and **blocking from the first stamp onward**: a resumed run has no stamps for work already in flight and must not be wedged by a gate it predates. `--ticket` is optional and every invocation without it behaves exactly as before — but when it *is* passed, the id is validated against the ticket graph first, because an id the graph has never heard of has no stamps and no dispatch record and therefore read to the gate exactly like a ticket that predates it: a one-character typo silently disarmed the merge gate while printing a reassuring line. A ledger that **exists but holds no usable verdict** is a veto, not a clean slate — `: > .swarm-loop/redcheck.jsonl` used to clear every veto in a run, and nothing but a normal `red-check` ever writes that file.

   **CLOSED, and the shape is worth keeping.** That evidence base was writable by the branch it judges: `redcheck.jsonl` was absent from git-guard's `LEDGER_NAMES`, so `: > .swarm-loop/redcheck.jsonl` and an `Edit` from the very worker being judged both sailed through while the same redirect onto `state.json` was blocked. It is in the list now, and so are `dispatch.jsonl` (which DATES a ticket — an undatable ticket is only advisory, so a forged line disarms the gate) and `findings.jsonl`. The list is enumerated once, in `references/run-permissions.md`, and `tests/test_harness.sh` fails if that enumeration drifts from the guard's own constant — because the four places that described the old list after it grew had each recited a *count* instead of the rule.
3. Compare the changed-file list against the task's ownership map. Scope creep (drive-by refactors of adjacent files) is grounds for rejection even when well-intentioned — it's the top source of cross-branch conflicts.
4. **Audit the branch's REMOVED LINES — over the WHOLE diff, not just its tests.** This is the check nothing else performs, and the one a green wave hides. The instruction is to read the **removed** lines, so ask git for those and nothing else; a raw `git diff` of a 5-branch wave is the loop's largest recurring context sink, and a tail truncated by the output cap is exactly where an unjustified deletion hides.

   **The `'*test*'` glob ORDERS that reading; it must never decide what is eligible to be read.** This step was scoped to test files, and that scoping is why a real fail-open shipped: a SOURCE-side deletion removed the failure path from a price parse, so the caller swallowed the exception and coerced the resulting empty value to zero — **a price that could not be parsed became a free item.** The orchestrator read all seven of that branch's deletions and signed them off as benign; the one that mattered was never in the set it read, on any branch at any rung, because the glob could not match it. It is the second time this scoping has cost something: the frozen-metric bypass, a two-line `pyproject.toml` that drove a metric from 50 to 100, also passed this audit precisely because the file did not match the glob. **A filter deciding what is *eligible* for review is a policy about what can be found, not a convenience.**

   The counter-failure is just as real — an unfiltered deletion dump is unreadable, and an instruction nobody can follow is another way of not being followed. So read it in this order. The two pathspecs **partition the range exactly** — probed on a real range: the test pathspec listed 1 file, its `:(exclude)` complement 4, and the unfiltered `--stat` the same 5 — so nothing falls out between them:

   ```bash
   R=main...task/<id>
   git diff -M -C --stat $R                                     # shape first: what moved, and how much
   git diff -M -C $R -- '*test*' | grep -E '^-[^-]'             # 1. tests — a weakened assertion is the highest-value find
   git diff -M -C $R -- . ':(exclude)*test*' | grep -E '^-[^-]' \
     | grep -Ei 'raise|throw|except|catch|assert|valid|verif|require|guard|abort|reject|return (False|None|null)|is None|!= *null'
                                                                # 2. source — the guard vocabulary, read first
   git diff -M -C $R -- . ':(exclude)*test*' | grep -E '^-[^-]'  # 3. the rest of the source side — read, never skipped
   ```

   `-M -C` is what keeps this tractable: without it a moved or renamed file dumps every one of its lines into the removed set and buries the handful that matter. Steps 1–3 are an ORDERING; step 3 is the whole source side and it gets read. **For each removed line, name what now happens on the path that line used to guard** — not "looks benign", but the sentence that says who reaches the code that line stood in front of, and with what value. That is the sentence the price-parse deletion could not have survived. And this pass is a first pass, never a verdict: the same reading is repeated over the **combined** integrated range at Phase 6 rung 2 (commands and order: `references/merge-protocol.md` step 9), because a deletion that is locally benign becomes a fail-open in combination with what the rest of the batch leaves around it — and because a clearance the orchestrator wrote is exactly what a second reader exists for.

   **Three dots, not two — this is load-bearing, do not "simplify" it back.** Three dots diffs the branch against its *merge base* (where it was cut from `main`); two dots diffs it against `main`'s **current tip**, which under this skill's rolling collection has already moved — every line a sibling landed on `main` while this branch was in flight is then charged to this branch as a removal, and the reject rule below would fire on a branch that removed nothing. It is also the same range `check-branch` printed in step 1. Past two or three branches in one collection pass, **delegate**: one read-only agent per branch, all at once (they cost no merge review, and one-per-branch is inside the fan-out budget), each briefed to return two lists and never the diff — "every removed or modified assertion, with the justification found in the diff and commit body, or the word MISSING", **and every removed SOURCE line that was a guard, each with the sentence naming what now happens on the path it used to stand in front of.** Brief both, always: an agent asked only for the assertions will hand back a clean report over the deletion that matters, exactly as the orchestrator did. Any modified/deleted assertion, widened tolerance, relaxed matcher, dropped parametrize case, new `skip`/`xfail`, or regenerated snapshot must carry a recorded `justify-test-edit` justification naming the requirement and answering *"would this still fail if the change were reverted?"*. **No justification → reject the branch**, even if every metric is green; a worker that quietly edits a test to fit its code has broken the verifier, and the metrics cannot see it. Additive tests need no justification — the asymmetry is the point.
5. Read the completion report; spot-check claims against the diff. A subagent saying "done" is a claim, not a fact — the measurement phase is the fact.
6. **Triage `BUGS-OBSERVED` and `NEEDS` from every report — including from rejected branches.** An `[open]` defect that blocks this cycle's integration or explains a currently red metric gets a **same-cycle hotfix dispatch** (fresh worktree, tight packet, the reporter's evidence pasted in); the rest go to the backlog with the evidence attached. A `[fixed]` item needs no dispatch — confirm the fix in the branch diff during this collection pass (it is a separate commit by contract). Never sit on a reported bug until "next cycle" out of habit — the report channel only works if reporting visibly causes action. **A `NEEDS` that names something frozen — a goal, an acceptance test, a protected path — is the worker's only sanctioned way to object to something it may never touch, so it is never dismissed silently.** It is either answered with evidence in the epoch report (the worker was mistaken, and here is why) or filed with `escalate` (the worker was right, and the user has to decide). Dropping it on the floor re-teaches the swarm that the wall has no door behind it, and the next worker's choice becomes silence or tampering.

**Two rung-1 triggers that fire on the diff, not on the report.**

- **A branch touching a shared `conftest.py`, a shared fixture, or any test-collection surface is an INTEGRATION change, not a local one** — it can break tests belonging to tickets that merged epochs ago. Gate it with a repo-wide `pytest --collect-only -q` across **every** test root and treat a collection **ERROR** as a veto rather than a count change; the failure and its evidence are in `references/merge-protocol.md` step 4.
- **A branch that adds or widens a CARVE-OUT in a gate rule must ship a committed file that exercises the carve-out — otherwise it is not a gate.** Reproduced: an import-linter contract gained a `** -> redis.exceptions` exemption to unblock four downstream tickets, and **nothing in the repo imported `redis.exceptions`**, so reverting the fix back to the broken single-star form *still passed*. The regression was invisible and would have landed on whichever ticket first wrote the legal code. This generalizes past linters to every allowlist, ignore-pattern, `# noqa` convention, exempted path and permitted-exception list: **an exemption no tracked file uses is untested configuration wearing a green tick.** Require the exercising file in the same branch, and a test that narrows the rule back and asserts non-zero exit.

Failed, hung, or rejected tasks: log what happened and *why* in the cycle report, return the task to the backlog annotated with the failure mode, and retire the worktree via the guard-safe path — `git worktree remove <worktree-root>/<id>`, using the `--worktree-root` chosen at Phase 0; **keep `task/<id>`** — its diff is the retry packet's input, and `retire` leaves it too. **`git worktree remove` is the sanctioned teardown, and the guard allows it** — the only form that validates what it deletes, refusing both a non-worktree path and one holding uncommitted work. `--force` and the `rm -rf` form are both blocked, so **there is no `rm -rf` fallback**; if a tree is wedged, salvage first — `--force` is a user-awake act, not an orchestrator one.

**External-limit deaths are not task faults.** A worker killed by a session cap, a credit limit, or an API 529 is *recovered*, not treated as a failed approach: inspect its worktree (`git -C <wt> status`) and salvage sound uncommitted artifacts (an `npm install` result is worth keeping); integrate finished peers first so re-dispatches branch off the richer HEAD; then re-dispatch the dead task with the same spec. And **never inherit a dead agent's green**: a worker that died before running its own verification leaves a hypothesis wearing a green suite — re-run the verification it didn't reach and write the tests it didn't write before believing the work.

**Wave-boundary tick (process loop).** Before dispatching the cycle's next wave, spend a moment on what this wave just taught you about the orchestration — a packet that lacked context, a boundary that was ambiguous, an ownership overlap the map missed, a task that was clearly two tasks. Append it to `.swarm-loop/learnings.md` — **curated as you append: merge it into a duplicate rather than adding one, and keep the file at roughly 30 entries, dropping the least useful when it overflows** — and apply it to the next wave's packets *now*, in this cycle (only the entries that bear on the ticket, never the whole file). This is what makes the loop self-improving from wave 1 of run 1 rather than from cycle 2 onward — the cheapest lessons are the ones applied minutes after they're learned.

## Phase 6 — Integrate

Follow **`references/merge-protocol.md`**. The shape: create `integration/<epoch>-<batch>` from `main` (one branch per integration batch); merge accepted branches **one at a time in dependency order** (most foundational first) — and before fixing that order, ask git which pairs actually collide: `python3 <skill>/scripts/swarmloop.py conflicts <ids> --base main` (merge-protocol step 3) is the only thing in this skill that compares two task branches' **actual content** to each other rather than to the globs their tickets declared, and it belongs here and nowhere earlier, because at check-wave time every lane still holds zero commits; after each merge run the fast checks (build + tests); resolve conflicts yourself, **in the primary checkout, on the integration branch step 2 created** — never inside an agent's branch, and **this protocol never creates an integration worktree and must not start** (rationale: `references/merge-protocol.md` step 5). For a one-sided conflict the guard **BLOCKS** `git checkout --ours/--theirs <file>` (and `-2`/`-3`) — probed exit 2 on all four, because the flags strip as options and the file operand reads as a pathspec. Take a side with `git show :2:<file> > <file>` (ours) or `:3:` (theirs), then `git add <file>` (probed exit 0, verified end-to-end). And a branch whose conflicts imply a design collision (not just textual overlap) gets rejected back to the backlog rather than hand-blended. When integration is green: merge to `main`; measurement and `checkpoint` happen in Phase 7 and **the push fires at the END of Phase 8**, after that epoch's ledger commit — **Phase 6 never touches a remote.** If integration cannot be made green, merge what is green, return the rest, and let the measurement record the truth.

**One integration check has no per-ticket equivalent, so it must be named here: run TWO LANES THAT SHARE A SURFACE TOGETHER, IN ONE PROCESS.** Locks, pools, singletons, module-level caches, fixed ports — every individual ticket's verify can pass while the *pair* deadlocks, and mid-run that detonates looking like a hang, the worst shape to diagnose. Single-ticket green says nothing about this class. Procedure and the 600-second self-deadlock it comes from: `references/merge-protocol.md` step 4.

Integration is serial; the loop around it is not. While merging a batch, tickets whose blast radius **and** dependencies are disjoint from every unmerged branch may already dispatch off current `main` — by construction they need nothing from the branches still in flight. What may never overlap: the measurement itself — Phase 7 runs against a settled `main`, after the epoch's merges are done.

### The verification ladder — every integrated batch, one unit, no exceptions

Terminology first, because the word is overloaded: **"verify"** names three things in this skill — the harness command (`swarmloop.py verify`, freeze integrity), **this ladder** (adversarial verification of built work), and the Phase 9 refuter. When any other document says "every build phase gets a verifier," read: **every integration batch.** Two anti-patterns are outlawed by name:

- **One verifier per build agent.** It duplicates rung 1's mechanized checks, is structurally blind to the cross-branch collisions that are the *actual* dominant failure mode (they only exist after integration), and doubles headcount to buy coverage of the wrong layer.
- **One verifier for the whole run or a multi-cycle "phase."** Unbounded context makes verification shallow, and defects surface late — a bug found five batches after it merged has been built on five times.

**Rung 1 — mechanized checks, every branch (Phase 5).** Deterministic, orchestrator-run: `check-branch`, scope audit, **removed-lines audit over the WHOLE diff**, report-vs-diff. The `'*test*'` glob ORDERS that reading — tests first, because a weakened assertion is the highest-value find — and never scopes it: a source-side deletion that removed a price parse's failure path (unparseable price → swallowed exception → zero → a free item) was ineligible to be seen under the glob on any branch at any rung, and the same glob is why the frozen-metric `pyproject.toml` bypass at the top of this file went unnoticed too. Commands and reading order: `references/merge-protocol.md` step 9. Necessary, never sufficient — no rung-1 pass is ever cited as "verified."

**Rung 2 — one adversarial verifier per integration batch. The default unit; always.** A read-only subagent that built *nothing* in the batch it judges, dispatched the moment the batch lands on `main` and running concurrently with the next batch's build (being async, this rung costs zero *wall-clock* — it is not free of anything else, and its width is the Phase-3 fan-out budget: **one verifier per collected branch plus one cross-cutting lens**, refutation severity-gated, per-finding dispatch bounded in the pattern). **Because it is async, keep a per-epoch list of which batches still have a verifier outstanding: the Phase 7 push gate waits on every one of them**, or a batch gets measured and shipped offsite before its verifier reports that the greens resolved out of the primary tree's `node_modules`. Its packet (variant in `references/task-packets.md`) carries the batch's ticket packets, the doers' reports **labeled as claims to test, not facts**, the integrated diff range, current metric values, and relevant learnings. Its duties: exercise each ticket's real path once through a real entry point and state *what the green is evidence of*; hunt cross-branch interactions (registries, schemas, shared assumptions); **check resolution provenance — did this batch's greens execute the branch's own source?** For at least one claim per ticket, print the path the runtime actually loaded (`require.resolve(…)`, `module.__file__`, `command -v` for a CLI) and confirm it sits inside the tree under test; a green that came from the primary checkout's `node_modules` or `.venv` is evidence about the wrong code, and `check-branch` cannot see it because it inspects a diff, not a resolution path; find callers of everything the batch added (CodeGraph **only if this verifier is running in the primary checkout** — a rung-2 verifier is read-only and may well be, which is fine; but the predicate is *which tree you are standing in*, not whether the repo is indexed, Phase 0) — zero callers means the wiring half was skipped; audit every claim against the diff — a dead or lazy agent leaves a hypothesis wearing a green suite; **re-read the batch's DELETIONS on the combined range** (`git diff main...integration/<epoch>-<batch>`, whole diff, ordering and commands in `references/merge-protocol.md` step 9) and, for each removed line, **name what now happens on the path that line used to guard** — because a deletion that is locally benign becomes a fail-open in combination with what the rest of the batch leaves around it, and because the per-branch clearance this re-reads was written by the orchestrator dispatching you: seven of one branch's deletions were read and signed off as benign, and the one that removed a price parse's failure path was caught only here, on the combined diff, after sign-off; and at deep depth, **sabotage in a scratch copy**: introduce the plausible wrong fix (never mere deletion), purge caches between variants, and prove the sabotage reached the code path before believing any result. It returns findings **with reproductions**, a **coverage map** (examined / not reached — named gaps become tickets), and a per-ticket verdict **with the evidence that earned it**. A verdict without evidence is not a verification: reject it and re-dispatch.

**Depth scales with the batch's contents, never with anxiety:**

| Batch contains | Depth |
|---|---|
| Docs, comments, purely additive tests | Rung 1 + a spot-check |
| Ordinary feature code | Standard: real-path exercise + claims audit + caller check |
| Shared interfaces, data models, migrations, auth/security, concurrency, anything in a frozen metric's blast radius | Deep: standard + sabotage + adversarial fixtures |
| Dead-agent salvage; a second attempt after rejection | Deep + rerun the verification the first attempt claimed to have done |

**Rung 3 — per-ticket deep verification, by trigger only.** Never as a default. Triggers: the deep-row categories above when a single ticket dominates a batch, a rung-2 coverage map naming a gap, or the orchestrator's own prescribed check turning out vacuous (validate the verification, not just run it).

**Rung 4 — the audit-fix loops and the frozen harness.** The harness sees only what acceptance exercises; the audit loops arrive after the build. Neither substitutes for rung 2, and rung 2 does not substitute for them.

Findings mint tickets through the Phase 5 triage machinery. A finding that invalidates a merged branch mints a fix ticket at the front of the frontier — or a revert per `references/merge-protocol.md` when the design itself is wrong. Verifiers rotate: a fresh verifier per batch, and no agent re-verifies work shaped by its own earlier findings without a second set of eyes at the next audit loop.

**Then RETIRE the batch's worktrees — at the verdicts, not at end-of-batch cleanup.** `python3 <skill>/scripts/swarmloop.py retire` (`--dry-run` first). A tree whose branch is an ancestor of `main` with no live agent has no consumer left and holds a gigabyte until retired. Conservative on purpose — **never merged-into-integration**: fix agents re-enter a ticket's worktree after adjudication. Contract, refusals and `checkpoint`'s warning: `references/merge-protocol.md` step 10.

## Phase 7 — Evaluate (the feedback in the loop)

**First, the gate on entering this phase at all: do not open a measurement epoch that landed no merges.** The stall counter is computed from a fingerprint of HEAD's tree with `.swarm-loop/` deliberately excluded, so it measures **the product tree, never the swarm's activity**. An epoch in which every worker is still building, in which every returned batch was rejected, or in which integration produced nothing green, lands a changeless fingerprint and increments that counter exactly as a genuinely spinning loop does — and `--stall-limit` of those in a row is `checkpoint` exit 2, a terminal signal you are told elsewhere never to argue with. That is how a healthy, wide, mid-flight run reports out with tickets open and workers still building. So: an epoch boundary exists only once **at least one branch has merged to `main` since the last `checkpoint`**. If nothing has, do not run the sequence below at all — stay in Phases 3–6, keep dispatching, collecting and integrating, and come here when a merge has landed. Rolling dispatch makes merge-less stretches ordinary; they are not epochs, and the counter must never be shown one.

If the cycle merged any dependency-manifest change (`package.json`/lockfile, `pyproject.toml`, …), **re-sync the primary measurement env first** — the same lockfile-selected installer the worktrees are provisioned with (`npm ci` / `pnpm install --frozen-lockfile` / `uv sync`, stack-appropriate) — because a stale-but-present dep dir reads as a false ZERO on the affected metrics, and that is an env-sync issue, never a code regression. Then, strict order, all through the script:

```bash
python3 <skill>/scripts/swarmloop.py verify                    # harness intact? if not: restore-harness, else scores are void
python3 <skill>/scripts/swarmloop.py measure --cycle N --timeout 2400   # every metric command; records value+error
python3 <skill>/scripts/swarmloop.py analyze --cycle N         # OLS per metric: slope, R², projection, verdict
                                                               # exit 1 = a metric had NO row at cycle N (stale) — the table is not a verdict on this cycle
python3 <skill>/scripts/swarmloop.py checkpoint --cycle N      # records HEAD, kill switch + budget, stale-worktree warning
```

**Bring the run's real dependencies UP before the sweep, and record PASSED / SKIPPED / DESELECTED beside every binary gate reading — a gate's number is uninterpretable without knowing what it did not run**, and a 0/1 gate is the worst offender because it reports the same `1` in both worlds. Two measured greens wearing the same name, and what each concealed: `references/goal-setting.md`.

Run the four one at a time and read each exit code — **never chain them with `&&`**, which silently skips `checkpoint` the moment `measure` exits 1. And `--timeout` is the **outer** cap, applied per metric command: **it must strictly exceed any timeout *inside* that command** (a `pytest --timeout=`, a `timeout N …` wrapper, a runner's own per-test cap), so the inner one always fires first. **The three inner forms are not equivalent, and the reason given here used to describe only one of them.** A runner-internal per-test cap (`pytest --timeout=`, a runner's own) fails one test and still prints a number — that is the good case, and the whole reason to want the inner one to fire first. A `timeout N …` WRAPPER does not: it kills the command outright, so it prints no number and `measure` appends no history row for that metric, exactly as the outer cap would. Prefer a runner-internal cap; a wrapper buys you only a faster failure, not a diagnosed one. The outer cap kills the whole command and records nothing either, converting a diagnosed failure into an undiagnosed one and leaving the inner process to be reaped rather than to report. Raise `--timeout` (or give the slow metric its own `"timeout"` field) — never lower an inner one to fit.

`analyze` fits ordinary least squares over each metric's per-cycle error and issues a verdict: `at_target`, `converging_on_track` (negative slope, projected error ≈ 0 by the final cycle), `converging_off_track` (improving, but the projection says it won't arrive in budget), `stalled`, `regressing`. Honest framing baked into the output: with ≤10 points this is trend detection for steering, not statistical inference — treat slope and projection as a signal, never as a proof.

**The goal-progress switch is a different question and does not need that gate.** It counts only cycles that actually produced measurements, and a cycle that measured nothing leaves it exactly where it was — so the merge-less-epoch hazard above does not apply to it. What it *is* telling you when it fires is the thing the fingerprint switch cannot say: the swarm has been busy and the numbers have not moved. Read `analysis/cycle-N.md` before reporting — the per-metric verdicts and the `Priority for next cycle` line name which goal is pinned and by how much.

**Exit semantics under the two-act shape.** `checkpoint` exit 2 (either kill switch, or the safety-ceiling) is **always terminal** — go to Termination. Its message says which fired: `no codebase changes for N consecutive cycles` is the fingerprint switch, `no graded metric has improved for N consecutive measured cycles` is the goal-progress one. `escalate --blocking` exit 2 is terminal in the same class and belongs in the same vocabulary — but it is a **different terminal state**, and calling it either "failed" or "done" is a misreport: an open blocking escalation means **the run is waiting on a human**, and nothing the loop can do clears it. Only the user does, by acting on the ask (`freeze --amend "<reason>"` where the ask was a goal change) and then `swarmloop.py escalate --resolve <ID>`. Say so plainly and first — the subject, the reason, and the proposed change — because a run that halts for a person and does not say what it is waiting for has spent the halt and bought nothing. Non-blocking escalations decide nothing here: they are surfaced by `analyze`, `resume` and `status`, carried into the epoch report, and the loop continues. `analyze` exit 2 (all targets met) is act-dependent: during the **build**, all-green plus an empty ticket ledger is the **build → audit transition**, not termination (all-green with tickets still open just means keep building); during the **audit-fix loops**, all-green is the expected steady state and decides nothing — only the loop budget or a clean audit ends the run. One honest caveat: with `--max-cycles` set as a generous ceiling, `analyze`'s projection-to-final-cycle is lenient — under dynamic scheduling, steer by the **verdict ordering** (regressing → stalled → off-track), not by the projection. And read exit 2 with its message: the terminal exits always print KILL SWITCH / budget-exhausted / all-met text, while a bad flag or subcommand exits **3** with a usage message — a usage error is never a terminal signal; fix the command and re-run. `measure` exit 1 and `analyze` exit 1 both mean THIS CYCLE IS NOT SCORABLE — a metric produced no number. Fix the measuring stick (or the env sync above) and re-run `measure --cycle N` before analyzing; re-measuring is safe because history.csv is append-only and analyze keeps the last row per cycle in file order. Still run `checkpoint --cycle N` — the stall counter and head_history depend on every cycle being checkpointed. A genuinely unmeasurable metric is entered by hand with `record --cycle N --metric <id> --value <n>` and said so in the cycle report — but **a hand-entered row does not buy all-green.** A stale metric can never read `at_target`, and a recorded one is withheld from the terminal signal by design: `analyze` refuses `all_targets_met` (exit **0**, not 2) while any metric's newest row is stamped `source=record`, printing every such metric by name and marking it `(MANUAL)` in the table. `analyze --cycle N --trust-manual-records` is the only override, it is **a USER-AWAKE decision** — never the orchestrator's, since the hand-entered row outranks the real measurement for its cycle — and it is recorded in the analysis JSON (`manual_records_trusted`) so the final report can say the transition was taken on a value nobody measured. So the build→audit transition stays unreachable until the metric is genuinely measured, or the user has approved trusting the hand-entered value.

**Never push before this phase — the Phase 7 gate is the loop's one and only push site,
gated here and FIRED at the end of Phase 8, after the ledger commit.** Nothing
else in the loop pushes: not Phase 6, not the merge protocol's cleanup step, not
Termination. Pushing on "tests green + types clean" skips the only thing that speaks for
the frozen goals; a regression found after the push costs a correction across every
remote and host, and it shipped in between. Measure, read the number, then push.

**The push step, last — after `checkpoint` AND after Phase 8's ledger commit.** The gate
is DEFINED here because the numbers it reads are here, and it EXECUTES at the end of
Phase 8, because its last condition is that Phase 8's commit has already happened. There
are two modes and only two: under `--push-remote never`, skip this step entirely — the
loop never touches a remote. Under `when-clean` (the default), push `main` only when all
of these hold:

- `verify` passed this epoch (a violated harness voids the scores, so there is no number to have read);
- `analyze` did not exit 1 — no metric is stale, so the epoch actually has values;
- this epoch's integrations landed green on `main` (the Phase 6 condition, unchanged);
- this epoch's tracked-file count is not an unexplained drop from the last. **The number is not eyeballed**: it is the one `checkpoint` just printed (`tracked files at HEAD: N`), against the previous entry in `state.json` → `head_history[].tracked_files`. `checkpoint` prints its own sharp-drop warning when the drop exceeds `max(25, 10% of the previous count)` — that warning is a push blocker until you have explained the drop in the epoch report, and a condition nobody sources a number for is a condition that passes vacuously every epoch;
- **every rung-2 verifier dispatched for this epoch's batches has returned, and none of its findings invalidates a branch merged into this epoch's `main`.** **Source this, do not recall it:** `swarmloop.py dispatch --list` prints every dispatch that was never closed, and an open one of **`--kind verifier`** here IS the unmet condition. Only that kind: dispatch is rolling by design, so an open *ticket* dispatch is the normal state of a wide mid-flight swarm, and reading the whole list as a blocker rebuilds the unsatisfiable gate of the bullet below in a new place — an unattended run would simply stop pushing, silently, for the same reason. `push-gate` draws the line the same way and prints the other open dispatches as context. Dispatch each verifier with `--branch <the branch it judges>` and close it with the same flag, so the record carries the SHA the verdict was measured against and says so out loud when the branch moved underneath it — a green about a tree that no longer exists is not a green, and this is the gate that would otherwise accept one. Rung 2 is deliberately async, so without this the push races it — and the finding it most often carries late is resolution provenance: greens that executed the primary tree's `node_modules` or `.venv` rather than the merged source. A verdict still outstanding is an unmet condition, not a pass; either wait for it (it costs no wall-clock to have dispatched it early) or carry the push to the next epoch's gate;
- everything `.swarm-loop/` currently holds is committed — **and that commit is Phase 8's, which is why this step runs at the END of Phase 8 and not here.** Nothing earlier can satisfy it: Phase 7's own four commands each write into `.swarm-loop/` — `measure` appends `history.csv`, `analyze` writes `analysis/cycle-N.json`, `checkpoint` rewrites `state.json` — so the moment the sequence above finishes, `git status` reads `M .swarm-loop/history.csv`, `M .swarm-loop/state.json`, `?? .swarm-loop/analysis/`. Reproduced on a fresh fixture: read as a Phase 7 condition this bullet was false in every epoch of every run, forever, and the failure was silent, because an orchestrator that never pushes prints nothing about not pushing — withholding the run's only offsite copy in exactly the unattended runs the rest of this section argues must not lose it. A push of a `main` carrying none of the epoch's evidence is what makes `resume` on a fresh clone useless.

Any one of those conditions unmet: **do not push**, name the failing item and why in the epoch
report — **and commit that amendment** (`git add .swarm-loop && git commit -m "cycle N: push
declined — <rung>"`) — then carry it to the next epoch's gate. That commit is not bookkeeping
pedantry: this gate runs at the END of Phase 8, so the report it is naming a failure in was
written **and committed** before the gate answered, and an uncommitted note re-dirties
`.swarm-loop/` and flips this gate's last rung to FAIL on the re-run — a refusal you created by
obeying this sentence. `push-gate`'s own refusal text says the same thing. **What does NOT gate the push is the
`analyze` verdicts** — a `regressing`, `stalled`, or `converging_off_track` metric is
Phase 8 steering, not a veto: those verdicts are trend detection over ≤10 points and
never proof (see the paragraph above), a mid-build metric moving the wrong way is a
routine state with a standing playbook entry, and blocking on it would withhold the run's
only offsite copy of `main` for an unbounded run of consecutive epochs, silently, in
exactly the unattended runs that most need it. Record the verdict and push the green
`main` anyway; what the measurement buys is that the number was read *before* the push,
not a veto over it. **`checkpoint` exiting 2 does not skip the push** either — kill
switch and budget-exhausted are terminal for the *loop*, not for this step: finish Phase
8's epoch report and ledger commit (the gate cannot clear without that commit), run the
gate, push if it clears, then go to Termination, or the final epoch's `main` is lost
offsite in precisely the abnormal endings where that matters most. **And if it does not
clear, that refusal is the last thing this run records**: append the named rung and why to
that final report and commit that too, because there is no next epoch's gate to carry it to
and Termination pushes nothing — an unrecorded final refusal is the silent non-push returning
in exactly the abnormal ending this paragraph exists to protect. A terminal exit ends
the *looping*, not the epoch you are standing in. When the loop pushes or deploys
anything, load the `verify-the-deploy` skill — verify each remote's SHA and the deploy target's HEAD
rather than trusting a command's exit or your own success message.

**Score the gate with the command, not from memory — `python3 <skill>/scripts/swarmloop.py
push-gate --cycle N`, at the end of Phase 8.** Exit 0 = the mechanical rungs are met,
exit 1 = do not push (it names which rung and why; `--push-remote never` is exit 1 too,
and says it is a configuration rather than a failure). It scores five of the seven
conditions above — `verify`, the cycle's analysis rows, the tracked-file arithmetic
(`checkpoint`'s own `max(25, 10%)` line, read out of `head_history`), open **verifier**
dispatches, and `.swarm-loop/` being clean — and **prints the other two as an operator
checklist it refuses to score**, on the pass path as loudly as on the fail path, because a
gate that quietly answers five of seven while looking like it answered seven is how a
green gets manufactured. Only `--kind verifier` dispatches block: dispatch is rolling by
design, so an open *ticket* dispatch is the normal state of a wide swarm and blocking on
it would rebuild the unsatisfiable gate somewhere else. A clean exit 0 is still not
permission — the two operator conditions are yours.

## Phase 8 — Adapt (close both loops)

**Product loop** — rewrite the backlog priorities from the verdicts:

- `regressing` → top priority; something merged this cycle broke it. **Rule out the measuring stick before diff-hunting the code**: a missed env re-sync, a metric command that walks a worktree or `.swarm-loop/`, and a config file a branch touched under a `?` tag all produce a `regressing` verdict with no product cause, and an epoch spent diff-hunting one of those is an epoch spent on the orchestration's own noise. Once the number is trusted, diff-hunt the cause and create a targeted fix task.
- `stalled` → the current approach isn't working; mandate a *different* approach in the new task packet (different design, different decomposition, more context), and say explicitly what was already tried. Re-running the same task is how stalls become kill-switch terminations.
- `converging_off_track` → the projection says effort is insufficient: allocate more of the next cycle to it, or split its tasks finer.
- `converging_on_track` / `at_target` → don't over-invest; protect them (regressions get caught next measure).

**A verdict the run itself disputes must not silently steer.** When an open escalation names a metric — you have told the user, in writing, that you believe its goal or its acceptance test is wrong — that metric's verdict stops being a mandate and becomes a disputed reading. Do **not** pour the next epoch's capacity into chasing a target you have already said is broken; that is the loop burning cycles against a goalpost it does not believe in. And do **not** quietly drop the metric from the table, deprioritize it without saying so, or reprioritize around it in silence — steering around a metric you have privately written off is the same failure as renegotiating the goal, just committed with the schedule instead of the file. Instead: keep measuring it, keep printing its real number and its real verdict with the escalation ID beside it in the epoch report, prioritize the tickets that would still be right whichever way the user rules, and take the rest of the frontier's ordering from the metrics nobody disputes. If the dispute leaves nothing honest left to build, that — and only that — is when the escalation earns `--blocking`.

**Process loop** — append to `.swarm-loop/learnings.md`: what about *the orchestration* failed or worked this cycle (task too big; packet missing context X; files Y and Z collided because the ownership map missed an import chain; wave 2 should have been sequenced). Next cycle's Phases 3–4 must apply these. Keep entries imperative and specific — they get injected into task packets, one relevant entry at a time and never the whole file — and **curated on every append: merge into an existing entry rather than adding a near-duplicate, and hold the file at roughly 30 entries.**

**Escalation sweep — a resolution un-blocks nothing by itself.** Run `swarmloop.py escalate --list --all` every epoch and read what changed since the last one. When the user resolves an escalation, the things that were parked on it stay parked until you move them: a ticket filed `--kind blocked-ticket` is still sitting in the backlog marked "waiting on ESC-*" and has to be put back on the frontier (or closed, if the user declined); a metric you had marked disputed goes back to steering the priorities normally, because its verdict is a mandate again; a branch rejected over a frozen-test objection has to be re-dispatched or the ticket re-planned against whatever the amend actually changed. Say in the epoch report, per resolved escalation, what the resolution released. An escalation that is resolved in the ledger and still blocking work in the backlog is the run silently keeping a wall the user already took down.

Write `.swarm-loop/reports/cycle-N.md` — and **delegate the writing**: hand a subagent the analysis table, the closed/minted ticket lines, the escalation list and the epoch's decisions, and have it return the report. Report prose is a recurring, purely-generative context cost and you hold the judgment either way. Contents: tickets closed this epoch (with their resolution, one line each), tickets minted (with source — worker report, verifier finding, audit), the analysis table, decisions for the next epoch, and **every escalation opened, still open, or resolved this epoch** (ID, kind, subject, proposed change, status) — an open one goes at the top of the report, because it is the part of the epoch that is waiting on the user rather than on the swarm.

**Every cycle report says the harness hermeticity is PARTIAL, and names the residual.** Never "sealed", never "the harness is intact" as if that settled the question. `verify` answers *did the frozen bytes move* — a real and load-bearing question, and a narrower one than *can this measurement be gamed*. The exploits a good frozen runner closes (plugin autoload disabled, `pythonpath` neutralized, discovery patterns pinned, project config overridden) are real closures — and **the structural one stays open**: product code imported by the suite runs **in the scorer's own process** and can tamper with its in-process state. That is inherent to any in-process black-box suite; it is not hardened away, only *moved* (subprocess-per-test), at a cost this design does not pay. `references/goal-setting.md` already says this about the `conftest.py` countermeasure specifically; it is true of the whole harness. State it every epoch, because **a harness described as sealed stops being audited, while one described as partial keeps being audited at exactly the seam that is still open.**

**Stamp every findings or handoff document with the skill commit it was written against** — `git -C <skill dir> rev-parse --short HEAD`. Without it a handoff keeps propagating findings that were fixed two commits ago, and the reader cannot tell a live defect from a closed one; measured, a handoff carried three already-fixed items forward. **And re-probe runtime facts at write time or mark them UNVERIFIED**: in one handoff three of seven STATE facts were wrong — a pid that named a dead process, a worktree count, a process count — while every fact that came from git (SHA, tracked count, cycle number) was right. The pattern is exact: what git can answer was accurate, what only the machine could answer was stale. A stale pid is the worst of them, because it sends a watchdog to monitor a corpse and reports healthy silence.

**Then commit `.swarm-loop/` — every epoch boundary, not just at freeze.** `git add .swarm-loop && git commit` covering `state.json`, `history.csv`, `analysis/cycle-N.json`, this epoch's `reports/cycle-N.md`, `backlog.md`, `learnings.md` and `codebase-map.md`. The freeze-time commit in Phase 2 step 4 is the *first* of these, never the only one, and two things break without the rest: the push below either ships a `main` carrying none of the run's evidence — and that push is the run's **only offsite copy** — or, because that commit is the last condition of its gate, does not fire at all — and a `resume` from a fresh clone finds no `.swarm-loop/` at all and cannot reconstruct the run. **This cannot reset the kill switch, by design**: `checkpoint`'s fingerprint hashes HEAD's tree *with `.swarm-loop/` excluded*, precisely so the loop's own mandatory bookkeeping commits cannot mask a changeless product tree. Do not "fix" that exclusion later, and do not skip these commits to protect the counter.

**Then, and only then, run Phase 7's push gate and push — `swarmloop.py push-gate --cycle N`, then push `main` if it clears.** This is where the push actually fires, not up in Phase 7: the gate's last condition is that the commit in the paragraph immediately above has already happened, and Phase 7's own `measure`/`analyze`/`checkpoint` each dirty `.swarm-loop/`, so at no earlier point in the epoch can that condition be true. The full gate — every condition, what the command scores, and the two it refuses to score — is Phase 7's; nothing about it is restated here, because two copies of a gate is how the two halves drift.

Then loop to Phase 3 while tickets remain; when the ledger is empty and the metrics are green (or every red is explained — and, where the explanation is that the goal itself is wrong, filed with `escalate` rather than argued in prose), take the build → audit transition.

**Ledger hygiene — no doc becomes an endless bug log.** The ticket ledger (`backlog.md`) holds **open tickets and scheduling constraints only**; a closed ticket leaves the ledger the epoch it closes, surviving only as its one-line entry in that epoch's report and in git history, and a scheduling constraint leaves the ledger with the last ticket it names. Raw `BUGS-OBSERVED` text is triaged at collection — minted into a ticket or dismissed with a one-line reason in the epoch report — and is never copied into any standing document; the ticket is the record. `learnings.md` stays process-only, imperative, and curated at every append. There is **no** "known issues" file, no cumulative bug register, no append-forever list anywhere in the repo: bounded history lives in the per-epoch reports, full history lives in git, and the final report summarizes both.

**`.swarm-loop/` is TWO halves and conflating them is what makes "never modify `.swarm-loop/`" contradict Phase 7's own gate.** The **hash-frozen** half — `goals.json` and `acceptance/` — is inside `manifest.json` and may change only through `freeze --amend`; `verify` re-hashes it every cycle and `check-branch` vetoes any branch whose diff touches it. The **append-only / per-epoch** half — `state.json`, `history.csv`, `analysis/`, `reports/`, `backlog.md`, `learnings.md`, `dispatch.jsonl`, `findings.jsonl`, `freeze-log.jsonl` — is orchestrator-owned and MUST be written and committed at every epoch boundary. "Never modify `.swarm-loop/`" is a rule for WORKERS about the first half; it was never a rule for the orchestrator about the second. One more distinction worth carrying: `freeze-log.jsonl` is append-only and tamper-evident but holds **no per-file hash map** — only `manifest.json` has those. An integrity check written against the log alone can re-hash nothing and will report clean over any modified file; `verify` gets this right by hashing against the manifest and authenticating the manifest against the log.

**And "anywhere" includes `.swarm-loop/` itself, which is where it actually goes wrong.** The sanctioned contents, in full: `goals.json`, `manifest.json`, `state.json`, `history.csv`, `freeze-log.jsonl`, `escalations.jsonl` + `ESCALATIONS.md` (append-only by design, and bounded by how many escalations a run genuinely files), `acceptance/`, `analysis/cycle-N.json`, `reports/cycle-N.md` and `reports/audit-loop-K.md` (one bounded file per epoch, which is the shape everything else should copy), `backlog.md` (open tickets and scheduling constraints only), `learnings.md` (~30 entries), and `codebase-map.md` (**rewritten in place, never appended to**). Anything else you put there is a working note and carries a size rule: **keep it under ~1,500 lines, and when a survey, review or intake report would exceed that, the output belongs in a subagent's brief and a bounded summary — not in a file the orchestrator will re-read every epoch.** Measured: one run's `.swarm-loop/` accumulated a 61 KB decisions file, an 87 KB intake report, a 75 KB public-surface dump and a 50 KB harness review, none of them named or bounded here, and two of them were the direct cause of tool-output-cap blowouts on reload. Any file that only ever grows is a defect in the run — fix it like one.

**Close the loop with a tool call, not with prose — in the two autonomy modes that run unattended.** The orchestrator is re-invoked only by a pending task: if the turn that closes cycle N ends with a summary and no dispatched agent, nothing wakes you, the loop silently halts, and it looks exactly like an API freeze. So under `approve-cycle-1` and `fully-autonomous`, dispatch the next cycle's first agent in the **same turn** you close the current one, *before* writing the closing summary. "I'll continue" is a statement; a dispatched agent is continuation. **The exception is `approve-every-cycle`, and it is not optional either**: that mode's whole content is that the user gates the next frontier, so the closing turn ends with the epoch report and *no* dispatch, and waiting is the correct behaviour rather than a stalled loop. Check the mode in `state.json` before deciding which of the two applies — dispatching under `approve-every-cycle` takes a gate the user asked for, and stopping under the other two silently ends the run.

## The audit-fix loops — Phases A1–A4 (after the build converges)

The build act ends with every ticket closed and the goals green — which proves the *tickets*, not the product. The audit act exists because the frozen metrics see only what acceptance exercises, and the wave verifiers saw only their own batches. The user set the loop count `N` at Phase 0; run exactly this per loop. **The four steps are numbered A1–A4 so a re-entry point inside the audit act can be named** — "resume at A3 of loop 2" is a position; "resume in the audit loops" is not. Record the current one alongside the loop number when you write anything down, and say it in the loop report.

**A1. Audit everything, in parallel, this loop and every loop.** Fan out read-only auditors **within the Phase-3 fan-out budget** — whole-project coverage is a property of the *union of partitions*, not of the agent count, so widen the partitions rather than the swarm; a loop that needs more than the cap runs in two passes and says so. Their partitions' union covers the entire codebase; rotate and overlap partitions across loops per the coverage invariant. Use the audit-packet variant in `references/task-packets.md`: adversarial framing (find what is wrong, not confirm), evidence and reproductions per finding, and a mandatory coverage map whose named gaps become targets.

**A2. Mint tickets from findings.** Each finding becomes a ticket with evidence, blast radius, and dependencies — or is dismissed with a one-line reason in the loop's report. No third state, and no standing findings list.

**A3. Resolve the loop's tickets through the same machinery** — Phases 3–8, unchanged and in full: frontier scheduling, isolated worktrees, fix-ticket packets (reproduce-first, root cause, sibling sweep), integration, wave verification, measurement, and Phase 8's adapt/report/commit. An audit loop can span several measurement epochs, and each of them is an ordinary epoch with its own `cycle-N.md` — the `audit-loop-K.md` at A4 summarizes the loop, it does not replace them. The frozen goals are re-measured; a fix that turns a metric red is caught the same epoch.

**A4. Close the loop** when its ticket set is empty: write `.swarm-loop/reports/audit-loop-K.md` (delegate the writing, as with the epoch report), commit `.swarm-loop/`, then record it — `swarmloop.py audit-loop-done` (add `--clean` when the audit minted zero tickets). The command tracks the act's progress in `state.json` and **exits 2 when terminal** (clean loop, or budget exhausted) exactly like the other terminal signals. Otherwise start the next loop **from scratch** — a fresh whole-codebase audit that assumes nothing from the last one.

**Early exit:** a loop whose audit mints zero tickets is a **clean loop** — the signal that auditing is done. Run Phase 9 below, then Termination, regardless of loops remaining. **Exhaustion:** finishing loop N without a clean loop also ends the run — the final report says so plainly, listing what the last loop still found; it does not talk itself into loop N+1.

## Phase 9 — The reverse loop: prune, only after a clean audit loop

Run this **only once an audit loop comes back with nothing worth fixing.** While real
defects are still being found, every hour spent on tidiness is an hour not spent on a
bug that reaches a user. Cleanliness is the reward for correctness, never a substitute.

The loop runs backwards: instead of *what is missing or wrong*, ask *what is here that
should not be*. Dead files, functions nobody calls, abandoned half-refactors, settings
nothing reads, tests that assert nothing, duplicated helpers, comments describing code
that no longer exists.

**The governing asymmetry — this is the whole design.** Leaving dead code costs
tidiness. Removing live code costs an outage, and it lands later, in production,
usually on the one path the suite never covered. **These are not comparable, so the
process is not symmetric:** a removal must be *positively proven dead*, and "I could
not find a caller" is not proof — it is the absence of proof, which is exactly what a
grep-shaped search returns for every dynamically-reached symbol.

### Three stages, all mandatory

1. **Propose (read-only).** Fan out auditors over disjoint areas. Each returns
   candidate removals, and each candidate MUST carry: what it is, why it is believed
   dead, **how the belief was established**, and the blast radius if the belief is
   wrong. No batch removals, no "delete this whole module" without a per-symbol case.
2. **Refute (independent, adversarial).** A *different* agent — never the proposer, and
   never seeded with the proposer's confidence — tries to prove each candidate is
   **alive**. Its job is to save the code, not to agree. It must actively hunt the ways
   static search lies:
   - dynamic dispatch, reflection, `getattr`/`__getattr__`, string-keyed registries
   - DI containers, plugin/entry-point registration, decorators that self-register
   - templates, config files, migrations, serialized data referencing a symbol by name
   - the public API surface (`__all__`, exported packages) — an external caller you
     cannot see is still a caller
   - tests are callers too; so are docs, examples, and the deploy
   - a symbol reached only in a mode this environment does not run (a flag that is off
     here, a dialect not used here, an OS branch)
   When a `.codegraph/` index exists **and this step is running in the primary
   checkout**, querying it for the candidate's callers and references is
   **mandatory before any grep-based deadness argument is admissible** —
   CodeGraph follows exactly the dynamic-dispatch hops (callbacks, registries,
   re-exports, JSX/DI wiring) that make grep-shaped searches lie about liveness.
   From a worktree there is no index to query and the CLI will answer from an
   unrelated one (Phase 0): say so explicitly, and treat the grep-only argument as
   the weaker evidence it is rather than as a satisfied requirement.
   A candidate survives **only** if the refuter fails to find life AND says what it
   tried. "No refutation found" from an agent that only ran the same grep is worthless.
3. **Approve (the orchestrator, personally).** Read the proposal and the refutation and
   decide. Delete nothing you cannot explain the deadness of in one sentence. When the
   two agents disagree, **go to ground truth yourself** — disagreement is signal, and
   averaging two opinions about whether code is reachable is how live code dies.

### Bias every judgment call toward keeping

- **Uncertain ⇒ keep.** An unremoved dead function costs nothing but a line count.
- **Recently added ⇒ keep.** It may be half-wired rather than dead — a mechanism whose
  callers are still coming. (This is a real and common shape: a correct implementation
  with zero call sites is *unfinished*, not *dead*, and deleting it destroys the work.)
- **Load-bearing-looking ⇒ keep.** Guards, validators, fail-closed branches, error paths
  and telemetry frequently look "unused" precisely because they only run when something
  goes wrong. **The success path is not the only path.**
- **Frozen/goal/acceptance anything ⇒ never remove.** Not even to tidy, and never as a pruning
  decision — tidiness is the weakest reason there is to move a goalpost. If a frozen artifact is
  genuinely *wrong* rather than merely untidy, that is an `escalate --kind frozen-goal` with the
  evidence, not a removal you make yourself.
- **Prefer proving deadness at runtime**: instrument, deploy, and observe zero hits over
  a real interval. That beats every static argument. If that is impractical, say so and
  keep.

### Land removals so they are cheap to undo
One concern per commit, never a mega-sweep; a commit body stating the evidence for
deadness and how it was refuted; the full suite AND the frozen metrics green after each.
A removal that cannot be reverted in one `git revert` is too big. Then **watch the
deployed system** — a deletion's failure mode is silence until the one caller you missed
runs.

## Termination and final report

**Context pressure is never a terminal signal.** The harness compacts and hands the work forward; everything load-bearing lives in `.swarm-loop/` and git precisely so that no session's context limit can end the run. The only terminal signals are the ones named below — if context is long, write the state down and keep going; do not editorialize a budget into a stop.

On any terminal signal — audit loops exhausted, a clean audit loop (via Phase 9), kill switch, the `--max-cycles` safety ceiling, an open **blocking escalation** (`escalate --blocking`, exit 2), an unrestorable harness violation, or the user's explicit stop — write `.swarm-loop/reports/final-report.md`. **Delegate the writing**, as with every epoch report: this is the largest generative output of the run and it arrives when your context is longest. Brief a subagent with the escalation list, the per-metric trajectories out of the analysis JSONs, the closed/abandoned/remaining ticket lines, the freeze-log records and the terminal signal, and have it return the report; you hold the judgment and check what comes back against the artifacts. Contents:

- **Every escalation, open or resolved — and any OPEN one comes first, above everything else in this report.** Straight from `swarmloop.py escalate --list` / `.swarm-loop/ESCALATIONS.md`: ID, kind, subject, the reason with its evidence, the specific proposed change, and status. An open escalation is the one item in the report that is waiting on the *user*, so it is the first thing they should see and the report must say what happens next (`freeze --amend "<reason>"` for a goal change, then `escalate --resolve <ID>`). If a blocking escalation is what ended the run, say that in the opening line: the run is **waiting on a human**, not done and not failed. A resolved one records what was asked, what the user decided, and which cycle it landed in. A run that ends with an unmentioned open escalation has silently swallowed the objection this whole channel exists to surface.
- Outcome per metric: baseline → final value, target, met or not, and the full per-cycle trajectory (the analysis JSONs have it all).
- What was built, what was attempted and abandoned (with why), and what remains on the backlog.
- **Any mid-run harness amend**, straight from `.swarm-loop/freeze-log.jsonl`: the `--amend` reason, the old→new hashes, and the cycle it landed in. A run whose goalposts moved must say so on its face — an unreported amend makes every trajectory above unreadable.
- If a kill switch fired: **say which one**, because they mean different things. `--stall-limit` consecutive checkpoints with an unchanged product tree means the loop was spinning, and the report should say what it was stuck on; state honestly if any of those checkpoints came from an epoch that landed no merges, because that is the loop having broken Phase 7's entry gate rather than the product having stalled, and it changes what the number means. `--goal-stall-limit` consecutive measured cycles with no improvement in any graded metric means something else entirely: the swarm *was* shipping code and the goals did not move. Name the pinned metric(s), their last value, their target, and what the cycle reports said was being worked on while they sat still — a run that built a great deal and moved no number is the single most important thing a final report can be honest about.
- **Self-improvement distillation — one command per lesson, because as a paragraph it was never once done.** Compress `.swarm-loop/learnings.md` into durable, project-agnostic lessons and promote each one:

    ```
    swarmloop.py distil --to-skill \
        --lesson  "<the imperative a future run should obey>" \
        --because "<the failure that motivated it>"
    ```

  That appends to `LEARNED.md` in this skill's directory, under a lock and byte-for-byte after the file it read. Two runs terminating at once therefore cannot *silently* lose each other's entry: the loser of the race is **refused outright** — told which lockfile blocked it and that nothing of its was written — and its entry IS lost unless you re-run the one command. That is deliberate (a lost update to memory every future run reads is worse than a re-run) but it is **not** a queue, so treat that refusal as work still owed. An orphaned lockfile self-clears after 120s. It never rewrites or reorders what is already there — **curation is still yours**, and merging a near-duplicate into an existing entry by hand beats adding a second one.

  It **refuses** rather than writing, and a refusal that names a real fault is the gate working, not an obstacle to route around: an entry naming a project, a path, a host, a product or a ticket (rewrite it naming the *role* that thing played); one that is a stub, over-long, a duplicate, or that narrates what happened instead of saying what to do; one whose lesson shares almost none of its distinctive vocabulary with the run's own `learnings.md` (record it in the run first — same command without `--to-skill`, which is also the default tier for the per-epoch process-loop append); and **the 41st entry**, which is refused with the capacity message and *not* trimmed to make room. `Never …`, `Always …`, `When X, do Y` and `Every ticket must …` are all accepted forms — and if a refusal ever names something that is **not true of your entry**, that is a defect in the gate: put it in the final report rather than mangling a correct lesson to appease a regex. If the capacity refusal fires, or if the append you just made filled the file, the refused lesson goes in this report under "proposed skill updates" and **you stop and tell the user in your next message**: a full `LEARNED.md` means the skill has a backlog, and the answer is an improvement pass that promotes every encodable entry into SKILL.md, the references or `swarmloop.py` itself. `swarmloop.py distil --list` shows where both tiers stand; `resume` and `checkpoint` print it every cycle, so a run that ends without distilling says so on its own face.

Present the final report to the user. **There is no push here** — the final epoch's Phase 7 gate either already pushed or already declined to, and the report says which. Do not push anything non-green as a parting gesture.

## Jira mirror (optional, when a Jira MCP is connected)

The loop mirrors itself onto a Jira scrum board so its progress is watchable in real time: epics per feature, a sprint per measurement epoch (and one per audit-fix loop, named "Audit loop K"), an issue per ticket transitioning **To Do → In Progress → In Review → Done** in lockstep with dispatch, collection, and merge, and the cycle analysis table posted to a Loop Control issue every cycle. Apply the hook table in **`references/jira-mirror.md`** at each phase boundary. Three invariants, argued fully in that reference: the mirror is **write-only** (board edits never steer the loop — talk to the orchestrator to change course), **never blocking** (Jira failures are queued and retried; the loop proceeds identically), and **harness-free** (`swarmloop.py` knows nothing about Jira, so the mirror layer is swappable).

## Resuming an interrupted run

Everything load-bearing lives in `.swarm-loop/` and git, not in any session's context — so a crashed or closed orchestrator session loses nothing but its place. To rejoin a run:

```bash
python3 <skill>/scripts/swarmloop.py resume
```

It reconstructs the situation from artifacts alone (no reliance on the dead session having marked anything): per-cycle completion flags (measured/analyzed/checkpointed/reported), harness integrity, live worktrees, unmerged `task/*` and `integration/*` branches, working-tree cleanliness — and prints a recommended re-entry point, including terminal conditions it detects (a clean or exhausted audit act, kill switch fired, safety ceiling hit, final report already written) and **every open escalation**. Read those first: an open blocking one means the previous session halted waiting on the user, so resuming without the user's answer just runs into the same wall — surface it again rather than quietly deciding it has been waiting long enough. All-green alone is **not** terminal: with audit loops still owed, `resume` reports it as the build→audit transition or the audit act's expected steady state — never as "go to Termination".

The recommendation is a heuristic; confirm it before acting. Reload the run's judgment from the latest cycle report, `learnings.md`, `backlog.md` and the codebase map — **but reload it the bounded way, because this reload is the single most expensive read the loop makes and doing it as four whole-file `cat`s has blown the tool-output cap twice.** `swarmloop.py status` and `resume` already print the state; `tail -n 80` the latest cycle report; and hand the rest to one read-only subagent with a brief naming what you need back ("the open tickets and their blockers, the learnings that bear on them, and anything in the map the last epoch's merges contradict"). Then rejoin at the indicated phase — and inside the audit act, name the **A1–A4 step** of the loop yourself from what `resume` and the last `audit-loop-K.md` report, because "somewhere in the audit loops" is not a re-entry point and the harness reports the loop number, not the step. Treat leftovers conservatively: run `check-branch` and the Phase 5 checks on any live branch before merging it; a worktree whose branch has no commits is a failed-hung task — reclaim it to the backlog. Confirm the live-worktree list against `git worktree list` yourself, since `resume` matches on the run's configured worktree path (`state.json` → `worktree_root`, set by Phase 0's `--worktree-root`): a run that never passed the flag will show **zero** live worktrees here no matter how many exist, and re-dispatching every in-flight ticket into a second set is the failure that follows. If the harness is reported violated, `swarmloop.py restore-harness` precedes everything else — never a re-`freeze`. Re-probe the git-guard (Phase 4) before the resumed session's first mutating wave: a resumed run is a fresh session and a fresh chance to be running unguarded — the file may have been moved, emptied or outranked since, and because hook config is re-read live on 2.1.259 (Phase 0), "it probed green last session" is not evidence about this one *and neither is the file still being on disk.* If a cycle was interrupted between measure and checkpoint, complete the evaluation sequence in order before adapting — never plan a cycle off a half-evaluated one. If the Jira mirror is enabled, reconcile the board once after resuming (board ← loop, per the mirror reference) so tickets match reconstructed reality.
